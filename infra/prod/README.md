# Прод-стенд на VPS (95.47.96.14)

Основной адрес — **https://stand.kenenai.com** (постоянный, сертификат
доверенный). Запасной — `https://95.47.96.14:4440`. Как это устроено и как
сменить адрес — раздел «Домен».

Один вход, сервисы разложены суффиксами пути — не портами.

| Путь | Что | Чем обслуживается |
| --- | --- | --- |
| `/` | витрина покупателя (чат-ассистент) | Next.js, контейнер `storefront` |
| `/app` | панель продавца/админа | Medusa admin из контейнера `backend` |
| `/picker/` | окно сборщика | статика Flutter web (`apps/partner`), отдаёт nginx |
| `/store` `/admin` `/auth` `/driver` `/media` `/static` `/health` | API | контейнер `backend` |

Витрина живёт в КОРНЕ, а панель — на своём родном `/app`: так не нужны ни
`basePath` в Next.js, ни смена `admin.path` в `medusa-config.ts`, и ни один
клиент не переучивается на новые префиксы API.

## Порты

Провайдер NAT-ит внешние порты на стандартные: **2240 → 22**, **8040 → 80**,
**4440 → 443**. Внутри nginx слушает 80 и 443, а порты опубликованы обеими
парами (`80:80`/`8040:80` и `443:443`/`4440:443`) — проброс сработает и если он
прямой. Прямой адрес стенда — `https://95.47.96.14:4440`; `http://…:8040`
отдаёт редирект на него (почему — ниже).

Основной вход через домен этих портов не использует вовсе: туннель открывает
исходящее соединение с сервера наружу. Это и есть причина, по которой домен
решает задачу, — нам не нужны ни 80, ни 443 снаружи.

## HTTPS обязателен для голоса

Голосовой ввод в чате работает ТОЛЬКО по https: браузеры отдают
`navigator.mediaDevices.getUserMedia` лишь в защищённом контексте, и по http
кнопка микрофона не показывается вовсе — так устроена проверка
`isVoiceRecordingSupported` в `storefront/src/lib/voice/voice-recorder.ts`.

Доверенный сертификат на голый IP получить нельзя: Let's Encrypt проверяет
владение через порт 80 (HTTP-01) или 443 (TLS-ALPN-01), а наружу провайдер
выводит только 8040/4440. Поэтому входов https **три**, и все рабочие:

| Вход | Адрес | Плюс | Минус |
| --- | --- | --- | --- |
| **Домен (основной)** | `https://stand.kenenai.com` | адрес постоянный, предупреждений нет, без порта | зависит от доступности Cloudflare |
| Прямой по IP | `https://95.47.96.14:4440` | работает, даже если туннель лежит | при первом заходе предупреждение браузера, «Дополнительно → Перейти» |
| Быстрый туннель | `https://<случайное>.trycloudflare.com` | не требует учётной записи | адрес меняется при каждом перезапуске сервиса `tunnel` |

Быстрый туннель остался запасным: именно его меняющийся адрес и подтолкнул
завести домен.

**HTTP отдаёт только редирект в HTTPS, и это не гигиена.** По незащищённому
соединению стенд не работает по существу: в production и Medusa, и витрина ставят
cookie с флагом `Secure`, поэтому по http не проходит ни вход в панель
(`/auth/session` отвечает 200 без `Set-Cookie`), ни вход покупателя по телефону —
причём оба ломаются МОЛЧА, возвращая на форму входа. Исключение — `/health`: он
остался на http для скриптов развёртывания и мониторинга.

По той же причине туннель ходит в nginx по **https**, а не по http: иначе nginx
видел бы незащищённое соединение, и вход в панель через туннель не работал бы.
Доверять заголовку `X-Forwarded-Proto` от cloudflared было бы проще, но это
значит верить заголовку, который может подделать любой клиент.

Самоподписанный сертификат выпускает `deploy-server.sh`, если файлов в `tls/`
ещё нет; вручную — `bash make-tls-cert.sh` (адреса возьмёт сам: домен из
`PUBLIC_ORIGIN` плюс IP). SAN обязателен, и тип записи разный: у IP — `IP:`, у
имени — `DNS:`; Chrome игнорирует CN. Приватный ключ в git не попадает.

Этот сертификат обслуживает запасной вход по IP и внутренний участок
`cloudflared → nginx`. На основном адресе посетитель видит сертификат
Cloudflare, а не этот.

Адрес быстрого туннеля виден только в логе:
`docker compose logs tunnel | grep trycloudflare`.

## Домен

Стенд живёт на `stand.kenenai.com` через **именованный туннель Cloudflare**.
Выбор такой, потому что провайдер не выводит наружу 80/443: без них не пройдёт
ни HTTP-01, ни TLS-ALPN-01, а `certbot` с DNS-проверкой дал бы адрес с портом
(`https://stand.kenenai.com:4440`) — порт в адресе остался бы навсегда. Туннель
открывает соединение изнутри наружу и снимает вопрос портов целиком.

Зона `kenenai.com` куплена в Cloudflare Registrar, поэтому DNS уже там и NS
делегировать не требовалось.

### Как настроен туннель

В панели Cloudflare (**Zero Trust → Networks → Tunnels**):

1. **Create a tunnel** → тип `Cloudflared` → имя, например `stroymarket-stand`.
2. Со страницы установки взять **токен** (строка вида `eyJhIjoi…`) — ставить
   cloudflared на сервер руками не нужно, он уже поднят контейнером `tunnel`.
3. Вкладка **Public Hostname** → **Add a public hostname**:
   - Subdomain `stand`, Domain `kenenai.com`, Path пустой;
   - Service: type **HTTPS**, URL `nginx:443`;
   - **Additional application settings → TLS → No TLS Verify: включить.**

Последний пункт обязателен и его легко пропустить. Туннель идёт в nginx по
**https** (по http Medusa не выставит cookie с флагом `Secure`, и вход в панель
молча не пройдёт), а сертификат на этом участке самоподписанный. У именованного
туннеля конфигурация origin'а живёт на стороне Cloudflare, и ключ
`--no-tls-verify` из `command` она НЕ читает — без галочки маршрут отвечает
`error 502`.

DNS-запись `stand.kenenai.com` Cloudflare создаёт сам при добавлении маршрута.

### Токен на сервере

Токен — секрет, поэтому задаётся скрытым вводом, без следа в истории команд.
В `.env` лежит не сам токен, а готовый хвост команды `cloudflared`:

```bash
ssh -t stroymarket 'cd ~/stroymarket/infra/prod && bash set-env.sh TUNNEL_RUN'
# ввести: run --token eyJhIjoi…
docker compose up -d tunnel     # окружение читается при СОЗДАНИИ контейнера
```

В файле значение окажется **в кавычках** — `TUNNEL_RUN="run --token eyJ…"`, их
проставляет `set-env.sh`. Это не косметика: `deploy-server.sh` читает `.env`
через `source`, и без кавычек bash принимает `--token` за команду, а
развёртывание падает на «`--token: command not found`» (наступили 2026-09-11).
Docker Compose кавычки снимает сам, так что формат годится обоим.

Почему хвост команды, а не токен: аргументы пришлось бы собирать из токена в
скрипте развёртывания, и тогда ручной `docker compose up -d` без скрипта молча
возвращал бы стенд на быстрый туннель со случайным адресом.

Пустой `TUNNEL_RUN` = быстрый туннель. Так режим виден в одном месте, и
`deploy-server.sh` в конце прямо пишет, какой из них поднят.

### Кэш Cloudflare и пересборка окна сборщика

Между посетителем и nginx теперь стоит кэш Cloudflare, и это меняет правила
выкладки статики. Сборка Flutter'а не содержит хэшей в именах файлов — каждая
пересборка кладёт тот же `main.dart.js` и `flutter_bootstrap.js`. Пока nginx не
присылал для них `Cache-Control`, Cloudflare применял свой дефолт для статики
(`max-age=14400`), и после выкладки домен ещё четыре часа отдавал СТАРУЮ сборку:
на диске и через nginx файл свежий, а через домен — `cf-cache-status: HIT` с
бандлом двухдневной давности и старым адресом бэкенда внутри (наступили
2026-09-11 при переезде на домен).

Лечится заголовком: `location /picker/` отдаёт `Cache-Control: no-cache`. Это не
«не кэшировать», а «кэшировать, но каждый раз спрашивать» — ETag остаётся,
неизменные файлы отдаются как 304.

Две особенности, которые стоит знать заранее:

- **Кэш у каждого краевого узла свой.** Проверка «с моей машины открылось
  правильно» ничего не доказывает: узел в Казахстане может держать другую копию.
  Проверять минимум с двух точек (`curl` с машины разработчика и `ssh` + `curl`
  с сервера) и смотреть на `cf-cache-status`.
- **Уже закэшированное заголовок не вытесняет.** Он действует со следующей
  выборки, а лежащая копия живёт до конца своего TTL. Разово чистится в панели:
  **Caching → Configuration → Purge Everything**.

Фото товаров (`/media/:file`) тоже лежат под постоянными именами и кэшируются
на стороне Cloudflare. Для стенда это скорее плюс, но при ЗАМЕНЕ фотографии
под тем же именем её придётся выбивать из кэша так же.

**Правка файла, примонтированного поодиночке, требует ПЕРЕСОЗДАНИЯ контейнера.**
`nginx-locations.conf` и `nginx.conf` монтируются как отдельные файлы, а такой
bind-mount привязан к inode. Доставка через `tar` создаёт файл заново, и
контейнер продолжает видеть прежнее содержимое: `nginx -t` проходит, `nginx -s
reload` отрабатывает, а конфигурация остаётся старой (наступили там же). Нужно
`docker compose up -d --force-recreate nginx`.

### Смена адреса стенда

Адрес размазан по пяти строкам `.env`, вшивается в бандл витрины и окна
сборщика на СБОРКЕ и вдобавок лежит абсолютными ссылками в базе — у фото
товаров (`/media/:file`) и PDF документов (`/static/:file`). Поэтому менять его
руками нельзя, есть скрипт:

```bash
ssh stroymarket 'cd ~/stroymarket/infra/prod && bash set-origin.sh https://stand.kenenai.com'
bash scripts/deploy.sh    # с машины разработчика: пересборка + выравнивание ссылок
```

`set-origin.sh` правит `PUBLIC_ORIGIN`, `STATIC_BASE_URL` и три `*_CORS`, причём
новый адрес в CORS **добавляется** к уже перечисленным — иначе переезд на домен
сломал бы запасной вход по IP.

Абсолютные ссылки в базе выравнивает `rebase-media-urls.ts`; `deploy-server.sh`
зовёт его на каждом развёртывании, и он идемпотентен. Без этого шага после
переезда фото каталога и ссылки на счета молча указывают на прежний адрес —
ошибок в логе при этом нет.

### Прогон после переезда

```bash
ssh stroymarket 'cd ~/stroymarket/infra/prod && bash smoke-stand.sh'
```

Проверяет не «открылась ли страница», а что каждая роль работает: страницы
`/ /app /picker/ /health`; вход админа, продавца и сборщика с cookie сессии под
флагом `Secure`; очередь заданий сборщика; вход покупателя по телефону; каталог
по публикуемому ключу; что в базе НЕ осталось ссылок на прежний адрес и что фото
товара и PDF счёта действительно отдаются; что окно сборщика несёт в бандле
текущий адрес. Учётки читает из `.env` и наружу не печатает.

Запасной вход по IP скрипт проверяет только по петле: с самого сервера внешний
адрес недоступен — NAT провайдера не разворачивает соединение обратно внутрь
(hairpin), и попытка даёт код `000`. Полная проверка внешнего входа — с машины
разработчика:

```bash
for p in /health /app /picker/; do curl -skI "https://95.47.96.14:4440$p" | head -1; done
```

## Развёртывание

С машины разработчика, из корня репозитория:

```bash
bash scripts/deploy.sh
```

Скрипт доставляет исходник (`tar` по ssh — rsync'а в Git Bash нет), фотографии
каталога (`backend/static` вне git), запускает `deploy-server.sh` на сервере и
собирает окно сборщика под `/picker/`.

**На ЧИСТОЙ базе миграции придётся прогнать отдельно** — в контейнере
`db:migrate` зависает (см. «Что осталось нерешённым»):

```bash
bash scripts/migrate-remote.sh   # миграции через ssh-туннель
bash scripts/deploy.sh           # повторно: шаг миграций будет пропущен
```

`deploy-server.sh` это учитывает: он проверяет число применённых миграций,
пропускает шаг, если они на месте, и держит на попытке жёсткий таймаут, чтобы
не висеть молча.

Предварительно на сервере нужен Docker:

```bash
sudo apt-get install -y docker.io docker-compose-v2 docker-buildx
sudo usermod -aG docker administrator
```

## Порядок шагов и почему он такой

`deploy-server.sh` идёт строго так:

1. `.env` — создаётся из `.env.example`, секреты и пароли учёток генерируются;
2. образ бэкенда → подъём `postgres`/`redis`/`backend` → ожидание `healthy`;
3. `db:migrate`;
4. фотографии каталога в том загрузок;
5. `bootstrap-store.ts` — канал продаж и **публикуемый ключ**;
6. `seed-kz.ts` (регион KZ, склады, категории, доставка) → `seed-demo-showcase.ts`
   (товары с фото);
7. учётки: админ, продавец, сборщики по категориям;
8. ключ вписывается в `.env` → сборка образа витрины → подъём витрины и nginx.

**Витрину нельзя собрать раньше шага 5.** `NEXT_PUBLIC_*` вшиваются в бандл
Next.js на сборке, а публикуемый ключ появляется только вместе с каналом продаж
на живой базе. По той же причине смена адреса стенда или флага `FEATURE_COMPANIES`
требует ПЕРЕСБОРКИ витрины, а не рестарта.

Скрипт идемпотентен: повторный запуск догоняет состояние, `.env` не
перезаписывается, сиды и создание учёток безопасны к повтору.

## Что осталось нерешённым

- **`medusa db:migrate` зависает в контейнере** (2026-09-08). После
  «Running migrations...» управление уходит в `MedusaAppMigrateUp` и не
  возвращается: ни одной миграции не применяется, в базе остаётся только
  `mikro_orm_migrations`. Замерено отладочным протоколом Node на зависшем
  процессе — событийный цикл держат живой сокет к Postgres и три таймера,
  ожидающих запросов нет. Воспроизводится из исходника и из прод-сборки, с
  `--concurrency 1`, `--skip-links`, `--skip-scripts`, при NODE_ENV
  `production` и `development`. При этом `medusa exec` и сам сервер в том же
  контейнере работают, то есть загрузка модулей не сломана — сломан только
  миграционный проход. Обход — `scripts/migrate-remote.sh` (ssh-туннель +
  локальный инструментарий). Причина не найдена; чинить или сообщать
  апстриму — отдельная задача.
- **Фото есть не у всех товаров каталога**: карточки профилей для гипсокартона
  приходят с `image_url: null` (проверено живым ответом ассистента). Пробел
  данных сида, не поломка.
- **Окно сборщика и витрина привязаны к адресу стенда на СБОРКЕ.** В `/picker/`
  origin вшит через `--dart-define=MEDUSA_BASE_URL` (`scripts/deploy.sh`), в
  витрину — через `NEXT_PUBLIC_*`. Поэтому по любому другому адресу (например,
  по запасному IP, если собрано под домен) страница откроется, но вход ответит
  «Нет связи с сервером». Сменить адрес — `set-origin.sh` + `scripts/deploy.sh`,
  рестарта недостаточно.
- **Запасной вход по IP предупреждает о сертификате.** Это цена того, что на
  голый IP доверенный сертификат не выдаётся. На основном адресе
  (`stand.kenenai.com`) предупреждения нет.
- **Основной адрес зависит от Cloudflare.** Туннель — единственный путь к
  домену: 80/443 наружу не выведены, поэтому при недоступности Cloudflare
  остаётся только вход по IP. Для стенда приемлемо; для боевой установки
  понадобится либо нормальный проброс портов от провайдера, либо другой хостинг.
- **Redis простаивает.** Контейнер поднят для паритета с локальной средой, но
  `medusa-config.ts` кэш и событийную шину на него не переводит — бэкенд работает
  на in-memory и потому масштабируется только одним инстансом.
- **Файлы лежат на диске сервера** (том `static`), не в S3 — задача T8.4.
- **Вход по номеру держится на dev-канале.** SMS-провайдера нет, поэтому
  `PHONE_OTP_DEV_CHANNEL=true` и на сервере: код входа возвращается в ответе и
  пишется в лог. Это ЕДИНСТВЕННЫЙ способ входа покупателя — выключать флаг можно
  только вместе с подключением провайдера.
- **Бэкапов базы нет.** Данные живут в томе `pgdata`.
