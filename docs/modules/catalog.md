# Модуль `catalog` — сегменты, модерация карточек, мульти-склад

**Статус:** реализованы модель `ProductCard` (модуль + link + миграция + тесты), workflows модерации
с subscriber'ом повторной модерации, store/admin API с OAS-фрагментами и админ-UI
(очередь модерации + widget карточки) ·
**Код:** `backend/src/modules/catalog/`, `backend/src/workflows/`, `backend/src/subscribers/product-updated.ts`,
`backend/src/api/store/products/`, `backend/src/api/admin/products/`,
`backend/src/admin/routes/product-moderation/`, `backend/src/admin/widgets/product-catalog-card.tsx`

## Назначение
Расширение каталога ядра Medusa под требования ТЗ: сегмент товара (эконом/комфорт/бизнес),
модерация карточек админом, сертификаты, ед. изм. Принцип — НЕ дублировать ядро:
всё, что ядро умеет, берём из ядра; кастом — только недостающие поля и переходы.

## Что закрывает ядро Medusa (не переизобретаем)
- **Иерархия «категория → подкатегория»** — `product_category` ядра (вложенные категории).
- **Карточка товара** — `product` (наименование, описание, фото `images`, характеристики
  `options`/`metadata`) + варианты (`sku` = код, `weight`/габариты — нужны логистике;
  фасовка — это варианты одного товара: «мешок 25 кг», «мешок 50 кг»).
- **Статусы модерации** — `product.status` ядра ровно повторяет флоу ТЗ:
  `draft` (черновик продавца) → `proposed` (на модерации) → `published` (одобрено) / `rejected` (отклонено).
  Store API отдаёт только `published` — скрытие неодобренных карточек от покупателя бесплатно.
- **Мульти-склад «город → склад → остаток»** — `stock_location` (город = `address.city`,
  верхний уровень иерархии; отдельная модель City не нужна) + inventory-модуль:
  `inventory_item` (на вариант) → `inventory_level` (остаток на складе) → `reservation` (резерв под заказ).
- **Остатки в реальном времени** — `inventory_level` в разрезе склада; агрегат по городу —
  сумма по складам с одинаковым `address.city`.

## Кастом: модель `ProductCard` (link 1:1 с product)
Недостающие ядру поля карточки (`backend/src/modules/catalog/models/product-card.ts`):
- `segment` — enum `economy | comfort | business` (обязателен, у каждого товара ровно один).
- `unit` — ед. изм. (`шт`, `мешок`, `м³`, `тонна`…) — текст, отображается на карточке.
- `certificates` — jsonb-массив `{ name, url }` (файлы в file-провайдере Medusa).
  Обязательны при отправке на модерацию (валидация в workflow, не в модели).
- `rejection_reason` — комментарий админа при отклонении (обязателен при reject, сбрасывается при approve).

Link: `backend/src/links/product-product-card.ts` (product ядра ↔ product_card, 1:1) —
FK на product в модели нет намеренно (правило изоляции модулей).

## Бизнес-правила (из ТЗ)
- Сегмент — у каждого товара, ровно один из трёх.
- Модерация: продавец создаёт карточку (`draft`) → отправляет на модерацию (`proposed`,
  сертификаты и сегмент обязательны) → админ одобряет (`published`) или отклоняет
  (`rejected` + обязательный комментарий).
- Изменение ключевых характеристик одобренной карточки → снова `proposed`.
  Реализация: subscriber на `product.updated` — цены и остатки этим событием не меняются
  (у них свои события price set / inventory), так что `product.updated` у `published`-товара ≈
  изменение карточки.
- До 5 складов на город: проверка count по `address.city` в middleware на
  `POST /admin/stock-locations` (ядро не ограничивает; своей модели склада не заводим).
  Реализовано — см. «Ограничение складов» ниже.
- Альтернативы при отсутствии товара (категория/сегмент/характеристики) — store-роут
  подбора, подзадача API.

## Workflows модерации (подзадача 2 — готово)
Код: `backend/src/workflows/` (шаги — в `steps/`), тесты — `integration-tests/http/catalog-workflows.spec.ts`.
- `create-product-card` — карточка модуля к существующему товару ядра + link 1:1
  (создание товара — ядро; вторая карточка на товар запрещена).
- `submit-product-for-moderation` — `draft|rejected` → `proposed`; валидация: карточка есть,
  сертификаты непусты (сегмент обязателен на уровне модели); сброс `rejection_reason`.
- `approve-product-card` — `proposed` → `published`, сброс `rejection_reason`.
- `reject-product-card` — `proposed` → `rejected`, комментарий обязателен (инвариант сервиса).
- `remoderate-product` — `published` → `proposed`; вызывается subscriber'ом.
- `update-product-card` — правка полей карточки (сегмент/ед.изм./сертификаты);
  у published-товара дополнительно переводит статус в `proposed` — правка нашей модели
  `product.updated` не эмитит, subscriber не сработает, поэтому переход явный в workflow.
- Subscriber `src/subscribers/product-updated.ts` — повторная модерация: правка published-товара
  с карточкой возвращает его в `proposed`.

Ключевое решение (см. DECISIONS 2026-07-14): статус меняется общим шагом `update-product-status`
через СЕРВИС модуля product (не через ядровый `updateProductsWorkflow`) — сервис не эмитит
`product.updated`, поэтому approve не зацикливается с subscriber'ом; событие эмитят только
правки через ядровые workflows (API продавца/админа).

## API (подзадача 3 — готово)
Код: `backend/src/api/store/products/` и `backend/src/api/admin/products/`,
тесты — `integration-tests/http/catalog-routes.spec.ts`, решения — DECISIONS (2026-07-14, API каталога).
- **Store, фильтр по сегменту** — параметр `?segment=` у ЯДРОВОГО `GET /store/products`
  (цены/каналы/пагинация ядра сохраняются). Middleware `filter-by-segment.ts` на
  wildcard-матчере `/store/products*` (wildcard регистрируются раньше статических ядровых
  валидаторов) вырезает `segment` до ядровой валидации и подменяет фильтром `id`
  (двухшагово: ids карточек по сегменту из модуля → пересечение с client-`id`;
  пусто → пустая страница сразу). Масштаб MVP ~1000 SKU это позволяет.
- **Store, остатки** — `GET /store/products/:id/availability`: вариант → города →
  склады (`город = stock_location.address.city`), `available = stocked − reserved`;
  неопубликованный товар → 404.
- **Store, альтернативы** — `GET /store/products/:id/alternatives?limit=1..20` (дефолт 5):
  published-товары той же категории и того же сегмента, исключая сам товар;
  товар без карточки → пустой список.
- **Admin, очередь модерации** — БЕЗ кастомного роута: ядровый
  `GET /admin/products?status[]=proposed&order=updated_at&q=...&fields=*product_card`
  (link отдаёт поля карточки, `q`/`order` — штатные).
- **Admin, действия** — `POST /admin/products/:id/moderation/{submit,approve,reject}`
  поверх workflows (reject — обязательный `reason`, zod в `admin/products/validators.ts`).
- **Admin, карточка (upsert)** — `POST /admin/products/:id/product-card` создаёт или
  обновляет карточку (роут выбирает workflow по наличию карточки; инварианты — в workflows).
  Правка карточки published-товара возвращает его в `proposed` (workflow
  `update-product-card`, см. ниже). В контракт admin-роуты не входят (спека — Store API).
- **Контракт** — фрагмент `store/products/products.oas.json`; для `segment` в ядровом пути
  используется `x-extendPaths` (расширение существующих операций в `generate-contract.mjs`).

## Ограничение складов + сид региона KZ (подзадача 5 — готово)
Код: `backend/src/api/admin/stock-locations/limit-per-city.ts`, `backend/src/scripts/seed-kz.ts`,

- **Ограничение ≤5 складов/город** — middleware `limitStockLocationsPerCity` на `POST /admin/stock-locations`

## Категории каталога — ровно четыре (T10.10)

Решение владельца 2026-08-25 (п. 3), уточнённое 2026-09-01: товары делятся РОВНО на четыре
категории ядровыми `product_category`, у товара ровно одна. Ассортимент магазина — черновая
отделка, инженерка и метизы; общестрой (песок, щебень, кирпич, арматура, блоки, пиломатериал,
кровля, утеплитель) снят с публикации.

| handle | Название | Что внутри |
|---|---|---|
| `finishing` | Отделочные материалы | гипсокартон и профиль, сухие смеси, штукатурки, шпаклёвки, грунтовки, краски, плитка, ленты |
| `electrical` | Электрика | кабель, автоматы, щиты, розетки и выключатели, подрозетники, гофра |
| `plumbing` | Сантехника | трубы, фитинги, краны, смесители, инсталляции, сифоны |
| `fasteners` | Крепёж (метизы) | болты, гайки, шурупы, саморезы, дюбели, анкеры, гвозди |

- **Источник правды** — `backend/src/lib/catalog/categories.ts` (handle, имя, описание, слова для
  разбора). Ищем и связываем ВСЕГДА по `handle`: имя владелец вправе переименовать в панели.
- **Заведение категорий** — `ensureCatalogCategories()` (`src/lib/catalog/ensure-catalog-categories.ts`),
  общая точка для сидов и миграции; идемпотентна. Внимание: `listProductCategories` без `select`
  отдаёт строки БЕЗ `handle` — карта handle → id молча получается пустой.
- **Классификатор** — `classifyProductCategory()` (`src/lib/catalog/classify-product-category.ts`):
  категорию задаёт ГЛАВНОЕ (первое) слово названия, и только если оно ни о чём не говорит —
  самое длинное совпавшее слово по всему названию. Поэтому «Саморез по гипсокартону» — метиз,
  а не отделка. Не попал никуда → `null`, и это не прячется.
- **Разбор существующего стенда** — `npx medusa exec ./src/scripts/apply-catalog-categories.ts`
  (сухой прогон; `... apply` — применить): проставляет каждому товару ровно одну категорию,
  а товар вне четырёх категорий снимает с публикации (`published` → `draft`), НЕ удаляя ни товар,
  ни остатки. Заодно гасит (`is_active = false`) категории вне четвёрки — остатки стартового сида
  Medusa («Merch», «Pants») и прежнюю общую «Строительные материалы»: иначе фильтр в панели
  предлагает девять категорий вместо четырёх.
- **Панель** — в очереди модерации колонка «Категория» и фильтр по ней (чипы фильтров вынесены в
  `src/admin/components/data-table-filter-chip.tsx`); список категорий берётся из ядрового
  `/admin/product-categories`, а не из константы.
- **Ассистент** — `search_products` возвращает название категории у каждого товара и принимает
  параметр `category` (handle): им сужают поиск и спрашивают ассортимент категории целиком
  (пустой `query` + `category` = обзор). В промпте — состав четырёх категорий и правило
  группировать список по категориям, когда позиций больше трёх.
- **Дальше по цепочке**: T10.11 (оплаченный заказ распадается на задания сборки — по одному на
  категорию), T10.13 (экран отгрузки), T11.3 (сметы по сегментам).

## Цены и остатки одним ресурсом (T10.14a, 2026-09-02)

Код: `backend/src/api/admin/price-stock/` (роуты + чистые правила `rows.ts` + выборки `load.ts`),
`backend/src/workflows/apply-price-stock.ts` и шаги `set-variant-prices.ts`,
`record-price-changes.ts`, `ensure-inventory-levels.ts`; модель журнала —
`backend/src/modules/catalog/models/price-change.ts`. Тесты: юниты
`src/api/admin/price-stock/__tests__/rows.unit.spec.ts`, живой путь —
`integration-tests/http/price-stock-routes.spec.ts`. Решения — DECISIONS 2026-09-02.

Источник правды по цене и остатку — ЯДРО (развилка №9, вариант «а»): своей таблицы нет, экран лишь
прячет цепочку «вариант → price set → цена» и «inventory item → level → остаток».

- **`GET /admin/price-stock`** — срез экрана. Строка = покупаемый ВАРИАНТ: товар, вариант, артикул,
  единица (из `ProductCard`), категория, цена в ₸, остаток / резерв / свободно, склад. Поиск `q` —
  по названию товара И по артикулу; фильтры — `category` (handle), `status`, чип `stock`
  (`zero` / `low`, порог `low_threshold` из настройки дашборда). Срез читается до потолка
  `scan_cap` (1000) и режется на страницы в памяти: строка — вариант, а пагинация ядра идёт по
  товарам, и «мало / нет» считается от СВОБОДНОГО остатка, которого ядро фильтром не отдаёт;
  счётчики чипов при этом полные.
- **Чипы категорий считает ресурс** (`category_counts`, T10.14e): по числу на каждую из четырёх
  категорий плюс мешок **`other` — «вне ассортимента»** (категория не из четвёрки или её нет
  вовсе). Ассортимент магазина — ровно четыре категории, и погашенные категории в чипы не идут, но
  позиции с ними живые: с экрана они не исчезают, и отфильтровать их есть чем (на стенде это
  13 черновиков снятого с продажи общестроя, висевших в таблице без фильтра). Поэтому фильтр
  категории применяется в ПАМЯТИ, после сборки строк: «не из четвёрки ИЛИ без категории» ядро
  фильтром не отдаёт, а счётчики чипов считаются по тому же срезу, что строки. Счётчик каждого чипа
  берётся по срезу ДО его собственного фильтра — чип показывает, что будет, если по нему нажать.
- **Разрез склада** — параметр `location_id`: числа строки по этому складу, `stocked_total` — сумма
  по всем. Склад один — берётся молча; без разреза при нескольких строка показывает сумму, а правка
  остатка требует назвать склад. Список складов приходит в ответе (`locations`) — экран рисует выбор
  без второго запроса.
- **`POST /admin/price-stock`** — партия правок цены и/или остатка (до 500 — потолок считается по
  импорту: файл применяется целиком, страница экрана в 50 строк проходит с запасом). Правка в строке — партия
  из одной позиции. Партия применяется целиком либо не применяется вовсе: при негодной позиции 400 и
  список `issues` с кодом и названием (`unknown_variant`, `empty_change`, `price_rules`,
  `stock_not_managed`, `location_required`, `unknown_location`, `duplicate_change` — позиция дважды
  в одной партии: обе правки считались бы от одного снимка, и дельты остатка сложились бы). Правка
  «в то же число» не пишется (`skipped`), а половина правки, совпавшая с текущим числом,
  вычёркивается — в журнал идёт только то, что менялось. В ответе — свежие строки задетых позиций в том же разрезе склада.
- **Что править нельзя** (`price_editable` / `stock_editable` в строке): цену, заданную правилами
  (регион/канал/количество) — она живёт в карточке товара; остаток, который не ведётся
  (`manage_inventory = false`) или у варианта несколько складских позиций.
- **`GET /admin/price-stock/history`** — журнал: кто, когда, было → стало. Фильтр `variant_id` даёт
  историю одной позиции (её же заберёт T11.6 в карточку товара). Ядро истории не хранит, поэтому
  факт правки пишется своей моделью `PriceChange` (снапшот названия и имени правившего; пустая пара
  `old_*`/`new_*` = «не трогали»).
  **У правки остатка назван СКЛАД** (`location_id` + `location_name` в строке; T10.14e): цена в
  магазине одна, а остаток у каждого склада свой, и «остаток 373 → 370» при двух складах не
  отвечает на вопрос «где». Названия складов роут подставляет по строкам своей страницы (как и в
  срезе экрана); склад мог быть удалён после правки — тогда остаётся правка без названия, а не
  пустая строка. У правки цены склада нет.
  **Подпись автора — правило на ЧТЕНИИ** (`api/admin/actor-label.ts`, T10.14e): имя учётки, а у
  учётки без имени — логин из почты без домена («admin@example.com» → «admin»). В модели остаётся
  честный снимок имени на момент правки, поэтому правило исправило подписи и у уже записанных
  строк; оно же применяется к «кто закрыл» в очереди отгрузки.
- **Запись** — workflow `apply-price-stock`: недостающий уровень остатка заводится нулём
  (`ensureInventoryLevelsStep`, обобщён на пары «позиция + склад»), остаток двигается ДЕЛЬТОЙ от
  снимка (`adjustInventoryLevelsStep`), цена пишется ядровым `updateProductVariantsWorkflow` (цены
  других валют проносятся без изменений), журнал — последним шагом.
- **Побочный эффект проверен:** правка цены эмитит `product-variant.updated`, а не
  `product.updated`, поэтому подписчик повторной модерации не возвращает товар на модерацию.
- Дальше по цепочке: T11.6 (история цены в карточке товара), T11.2 (свободный остаток покупателю —
  обязан показывать ту же цифру).

## Экран «Цены и остатки» (T10.14b, 2026-09-02)

Код: `backend/src/admin/routes/price-stock/page.tsx` (экран), `lib/price-stock.ts` (DTO ресурса и
правила клетки — под юнитами `src/admin/lib/__tests__/price-stock.unit.spec.ts`),
`hooks/use-price-stock.ts` (запись партии), `components/price-stock-bulk-drawer.tsx` (массовая
правка), `components/price-stock-history-drawer.tsx` (журнал), `styles/price-stock.css`. Пункт
сайдбара — сразу за «Товарами», перед ядровым «Складом» (порядок — `styles/shell.css`). Кадры гейта
U — `docs/qa/screens/T10.14b/`, отчёт `docs/qa/2026-09-02-T10.14b-ui.md`.

- **Правка живёт в клетке, а запись — партией.** Набранное в полях — черновик экрана: в каталог
  ничего не уходит до «Применить», потому что ресурс пишет партию целиком либо не пишет вовсе, и
  продавец, правящий двадцать строк, должен видеть их все перед записью. Массовая правка выделенных
  тоже пишет в ЧЕРНОВИК (одно число во все выделенные строки), а не в каталог: путь записи один.
  Enter в клетке = «Применить» (клавиатурных сокращений ядрового CommandBar на экране нет — руки
  продавца всё время в полях ввода, и одна буква мимо поля стирала бы набранное).
- **Черновики живут по позициям, а не по странице:** строки, которые экран видел, кешируются, и
  партия собирается по ним даже после перехода на другую страницу. Смена склада отменяет набранные
  ОСТАТКИ (число набрано для склада, который на экране) и оставляет цены — со подтверждением.
- **Запертая клетка объясняет себя**: вместо поля — текущее число, приписка («по правилам», «не
  ведётся», «выберите склад») и подсказка при наведении. Отказ партии — списком позиций под
  таблицей (`issues` из 400), а не растворяющимся тостом; поэтому запись идёт голым `fetch`, а не
  `sdk.client.fetch`: js-sdk оставляет от тела ответа одно `message`.
- **Копейки в клетке не превращаются в сотни (T10.14d, блокер Ф-прогона Данияра).** Разделитель
  дробной части сохраняется в тексте клетки, а не выбрасывается вместе с пробелами-разрядами:
  раньше «2 750,00» из прайса поставщика склеивалось в 275 000 ₸ и уходило в каталог молча. Дробное
  число правкой не считается (`parseAmountInput` → null) — **то же правило, что у импорта файла**;
  клетка обводится ошибкой, над таблицей встаёт «Клеток с копейками: N — партия не записана», а
  «Применить» и Enter заперты, пока такая клетка есть. Пробел-разделитель тысяч по-прежнему
  снимается: «6 000» — шесть тысяч.
- **Выделение не переживает смену задачи (T10.14d, блокер того же прогона).** Галочки снимаются при
  смене поиска, чипа категории, чипа остатка, склада и ПОСЛЕ записи: иначе продавец, выделивший две
  строки и сменивший поиск, подставлял число в позиции, которых на экране нет. Выделение по
  СТРАНИЦАМ осталось (оно нужно), но пока часть выделения вне видимого среза, панель говорит
  «Выделено: 2 · вне экрана: 2», а drawer массовой правки называет эти позиции поимённо — записывать
  вслепую экран не даёт.
- **Плитка дашборда и экран считают ОДИН срез (T10.14e).** «Низкие остатки» на дашборде считались
  по складским позициям ядра (`inventory_item`), и в счёт попадала позиция, заведённая приходом без
  карточки товара: плитка говорила «1 — ноль на складе», а на экране остатков её не было
  (`KZ-SAND-BB1`: в ядре 53 позиции, в срезе 52). Теперь `loadStock` дашборда зовёт тот же
  `loadPriceStockSlice`, плитка и панель ведут на `/app/price-stock?stock=low`, а экран читает чип
  остатка из адреса. Следствие: безкарточные складские позиции видит только владелец в ядровом
  «Складе» — вопрос владельцу (запрет в приёмке или отдельный показатель).
- **Ядровый «Склад» у продавца скрыт** (`styles/shell.css`, T10.14e): кладовщик шёл в раздел по
  названию и попадал в таблицу складских позиций без названий товаров. У владельца пункт остаётся —
  там резервы, переучёт и позиции без карточки.
- **Раскладка таблицы — авторастяжная, не `fixed`:** при `table-layout: fixed` ядровые
  sticky-колонки (чекбокс и первая колонка данных) получают клетку шире слота и накрывают соседнюю
  (у колонки «Категория» пропадало начало текста). Разрастание колонки товара держит ограничение
  ширины названия, а клетки с полями — свой `min-width`, иначе узкий экран давил поле ввода в щель.

## Обмен файлом: выгрузка и загрузка (T10.14c, 2026-09-02)

Код: `backend/src/api/admin/price-stock/csv.ts` (формат: кодировка, разбор и сборка таблицы, числа),
`import.ts` (сверка файла с каталогом), `export.ts` (колонки выгрузки), роуты `export/route.ts` и
`import/route.ts`; экран — `hooks/use-price-stock-import.ts`,
`components/price-stock-import-drawer.tsx`, `lib/price-stock-import.ts`. Юниты —
`src/api/admin/price-stock/__tests__/{csv,import}.unit.spec.ts`, живой путь — в
`integration-tests/http/price-stock-routes.spec.ts`. Кадры гейта U — `docs/qa/screens/T10.14c/`,
отчёт `docs/qa/2026-09-02-T10.14c-ui.md`.

- **Формат — CSV с «;» и BOM.** Русский Excel открывает такой файл двойным щелчком и сохраняет
  обратно без мастера импорта; своего разбора .xlsx не заводим (бинарный формат = зависимость ради
  одного экрана). При ЧТЕНИИ разделитель определяется сам («;», запятая, табуляция, метка `sep=`),
  а кодировка распознаётся: UTF-8 с BOM и без, windows-1251 (ANSI — умолчание русского Excel) и
  UTF-16 («Юникод-текст»).
- **Ключ строки файла — АРТИКУЛ, а не id варианта.** Файл — то же рабочее место продавца, что и
  экран, и технических id на нём нет (DoD T10.14). Позиция без артикула выгружается с пометкой
  «нет артикула» и обратно не загружается. Сверка артикула — без учёта регистра.
- **`GET /admin/price-stock/export`** — тот же срез, что на экране (склад, поиск, чипы), но ЦЕЛИКОМ,
  а не страницей: срез собирает общий `loadPriceStockSlice`, которым живёт и сам экран — иначе
  «выгрузить то, что вижу» разъехалось бы с тем, что видно. Колонки: Артикул, Товар, Категория,
  Единица, Цена ₸, Остаток, Свободно, Склад («Свободно» — только для чтения, импорт её не понимает).
- **`POST /admin/price-stock/import` НИЧЕГО не пишет** — это предпросмотр: строки файла сверяются с
  каталогом, и наружу идут пары «было → станет», список непринятых строк и ГОТОВАЯ партия. Пишет её
  тот же `POST /admin/price-stock` с `source: "import"` — путь записи один, и партия по-прежнему
  применяется целиком либо не применяется вовсе.
- **Пустая клетка — «не трогаем», а не ноль.** Число читается так, как его пишет Excel («2 600,00»,
  неразрывный пробел в разрядах, знак ₸), дробное — отвергается, а не округляется: цена в тенге
  целая, и молча менять деньги продавца нельзя. Клетка с тем же числом, что в каталоге, правкой не
  считается (продавец выгрузил весь срез, а поправил в нём десять строк) — поэтому файл, применённый
  дважды, каталог не трогает.
- **Причина по строке, а не «файл плохой»:** `missing_sku`, `unknown_sku`, `duplicate_sku`,
  `bad_price` / `fraction_price`, `bad_stock` / `fraction_stock`, `price_rules`,
  `stock_not_managed`, `location_required` — с номером строки В ФАЙЛЕ (её продавец ищет в Excel) и
  названием товара. Файл целиком не принимается только по причинам, при которых сверять нечего:
  `empty_file`, `no_columns`, `too_many_rows`, `mixed_locations`, `unknown_location`,
  `location_mismatch`, `too_many_changes`.
- **Склад файла и склад экрана обязаны совпадать.** Колонка «Склад» в выгрузке — не украшение:
  файл, выгруженный по одному складу и загруженный при другом разрезе, увёл бы остатки не туда
  незаметно. Один склад в файле = целевой склад записи; несколько разных — отказ; если колонки нет,
  берётся разрез экрана.
