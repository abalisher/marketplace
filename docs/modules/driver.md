# Модуль `driver` — водитель-gig: профиль и допуск к работе

**Статус:** реализован (T5.1, 2026-09-04); раздел «Водители» в панели продавца — T5.1a (2026-09-04).
**Код:** `backend/src/modules/driver/` (модель + сервис + миграция),
workflows `backend/src/workflows/{verify-driver-otp,update-driver-profile,set-driver-status}.ts`
+ шаги `steps/{verify-driver-otp,register-driver,issue-driver-session,update-driver-profile,set-driver-status}.ts`,
роуты `backend/src/api/driver/*` (поверхность водителя) и `backend/src/api/admin/drivers/*` (панель продавца),
CORS для своего префикса — `backend/src/api/utils/driver-cors.ts`,
экраны панели — `backend/src/admin/routes/drivers/` (очередь и карточка).

## Назначение
Водитель НЕ сотрудник продавца (решение владельца 2026-08-25, п. 5): любой из пула знакомых
водителей **сам регистрируется** по номеру телефона в приложении `apps/driver`, сам заполняет
профиль (ФИО, машина, грузоподъёмность) и после проверки продавцом берёт заказы. Отсюда свой
**actor_type `driver`** и своя поверхность API `/driver/*` — это и закрывает отложенный «гэп ролей 7».

Модуль отвечает ТОЛЬКО за человека и его допуск. Как заказ физически везут (рейсы, точки, proof
выдачи, GPS) — модуль `logistics`; он ссылается на водителя опазной колонкой `driver_id`
(модули не импортируем).

С T5.2b водитель ещё и **актор перехода заказа**: отметка «выдано» на точке рейса переводит заказ в
`delivered` с `actor_type = driver`, и его имя в логу переходов панель берёт из этого модуля
(`api/admin/orders/[id]/lifecycle/actor-names.ts`).

## Что закрывает ядро Medusa (не переизобретаем)
- **Auth-модуль** (`Modules.AUTH`): учётная сущность (`auth_identity`) и провайдер-идентичность
  (`provider = "phone"`, `entity_id` = номер). Наш провайдер `auth-phone` (T10.7) проверяет код —
  он общий с покупателем, см. «Одна учётка, разные actor-типы».
- **Аутентификация запросов**: штатный middleware `authenticate("driver", ["bearer"])` принимает
  наш токен как ядровый — actor-тип у Medusa произвольный, отдельного слоя не нужно.
- **Связь учётки с профилем**: ядровый шаг `setAuthAppMetadataStep` (`app_metadata.driver_id`).

Своя таблица только одна — `driver` (профиль и допуск).

## Модель `Driver`
| Поле | Смысл |
|---|---|
| `id` | `drv_*` |
| `phone` | номер в каноне `+7XXXXXXXXXX`, **уникален** среди живых записей (он же ключ учётки) |
| `full_name` | ФИО — заполняет сам водитель |
| `vehicle_model` / `vehicle_plate` | машина: модель для пула заказов, госномер для склада и сверки на выдаче (хранится в верхнем регистре) |
| `capacity_kg` | грузоподъёмность, кг — по ней подбирают машину под заказ |
| `status` | допуск: `pending` / `active` / `blocked` |
| `status_note` | причина отказа/блокировки — её водитель видит у себя в приложении |
| `status_changed_at` / `status_changed_by` | когда и кто из панели решил (`user_id`, опазная ссылка) |

## Допуск к работе (стейт-машина)
```
pending ──► active ──► blocked
   └────► blocked ◄────┘   blocked ──► active
```
- `pending` — водитель зарегистрировался, заявка ждёт проверки продавцом. **Самрегистрация ≠
  мгновенный доступ**: водитель везёт чужой товар и чужие деньги, поэтому заявку смотрит человек
  (владельцу вынесена развилка — см. ниже).
- `active` — допущен; только такой водитель видит пул заказов и может взять заказ. Гейт стоит
  отдельным middleware (`api/utils/require-active-driver.ts`, T5.2a): токен выдаётся при ЛЮБОМ
  статусе заявки, поэтому доступ к работе проверяется не токеном, а статусом — 403 с причиной,
  которую написал продавец.
- `blocked` — доступ закрыт. Отказ по заявке и блокировка позже — ОДНО состояние, различает их
  `status_note`. Блокировка обратима (`blocked → active`).
- Вернуть в `pending` нельзя: это состояние заводит только сама регистрация.
- **Допустить незаполненный профиль нельзя**: без ФИО и госномера продавцу нечего проверять
  (`assertDriverActivation`); признак `profile_complete` считает сервер и отдаёт клиенту готовым.

## Одна учётка, разные actor-типы
Номер телефона — ключ учётной сущности человека, а не роли. Поэтому водитель и покупатель с одним
номером живут на ОДНОЙ `auth_identity`: рядом в `app_metadata` лежат `customer_id` и `driver_id`,
а различает их **actor_type токена** (`customer` / `driver`). Следствия:
- вход водителя переиспользует провайдер `phone` и workflow запроса кода целиком — код входа один
  и тот же и подтверждает только владение номером; какую сессию он откроет, решает роут, куда его
  прислали;
- **пауза «выслать снова» у обеих поверхностей общая** (состояние кода живёт в
  `provider_metadata` одной провайдер-идентичности) — запросив код в приложении водителя, тот же
  человек минуту не получит код на витрине. Это один человек и один номер, поэтому ограничение
  считаем корректным;
- токен водителя не открывает ни `/store/*`, ни `/admin/*`, и наоборот (покрыто тестом).

## API
| Роут | Кто | Что делает |
|---|---|---|
| `POST /driver/auth/phone/otp` | без токена | запрос кода: `{ phone }` → `{ phone, expires_in, resend_after, dev_code }`; 400 — не мобильный номер, 429 — пауза |
| `POST /driver/auth/phone/verify` | без токена | подтверждение: `{ phone, code }` → `{ token, driver, created }`; 401 — `invalid_code`/`code_expired`, 429 — `too_many_attempts` |
| `GET /driver/me` | водитель | свой профиль и свой допуск (`id` — из токена, параметром не передаётся) |
| `POST /driver/me` | водитель | заполнить/поправить профиль: `full_name`, `vehicle_model`, `vehicle_plate`, `capacity_kg` (любое подмножество; `null` очищает) |
| `GET /admin/drivers` | панель | очередь водителей: фильтр `status`, поиск `q` (номер/ФИО), пагинация; FIFO — кто подал заявку раньше |
| `GET /admin/drivers/:id` | панель | карточка водителя |
| `POST /admin/drivers/:id/status` | панель | решение: `{ status: active\|blocked, note? }`; кто решил — из учётки |

Три admin-роута отдают не общий `DriverView`, а свой `AdminDriverView`
(`api/admin/drivers/driver-admin-view.ts`): к профилю добавлено
`status_changed_by_name` — ИМЯ решившего (идиома `api/admin/user-names.ts`).
`status_changed_by` (`usr_01H…`) наружу не уходит вовсе: id учётки на экране ничего не
объясняет, а водителю в приложении решения продавца вообще не показываются — у него только
статус и причина.

Работа водителя с заказами живёт не здесь: `GET /driver/orders` (пул) и
`POST /driver/orders/:id/claim` («взять заказ») — поверхность модуля `logistics`
(`docs/modules/logistics.md`, раздел «Gig-модель»). Здесь только человек и его допуск.

Вход = регистрация: первый верный код по незнакомому номеру заводит заявку (`created: true`), и
приложение сразу ведёт водителя заполнять профиль. Токен выдаётся при ЛЮБОМ допуске — иначе
заблокированный водитель увидел бы «неверный код» вместо причины отказа.

CORS для `/driver/*` ставит свой middleware (`api/utils/driver-cors.ts`): ядро знает только свои
префиксы (`/store`, `/admin`, `/auth`), а web-сборка приложения водителя ходит из браузера.
Список origin'ов — общий с витриной и мобилкой (`lib/cors-origins.ts`).

## События
- `driver.registered` — пришла новая заявка (продавцу — на проверку).
- `driver.status_changed` — допуск изменён (`from`/`to`/`note`).

Подписчиков пока нет: уведомление водителю о решении придёт с notification-провайдером (отдельная
задача, как и у `logistics`).

## Открытые вопросы (гейты и развилки)
- **Развилка владельцу:** заявка водителя проходит проверку человеком (`pending → active`) или
  регистрация сразу допускает к пулу? Сейчас — проверка; если водители «свои и знакомые», можно
  включить авто-допуск (это одна строка в `registerDriver`).
- **Гейт В (общий с покупателем):** SMS-провайдера на MVP нет — код входа живёт в dev-канале
  (`PHONE_OTP_DEV_CHANNEL`, см. `auth-phone.md`).
- Личные данные для выплат gig-водителю (ИИН, реквизиты) в профиле НЕ хранятся — вопрос выплат
  владельцем не решён.
- Контракт: `status_changed_by_name` появился ПОСЛЕ генерации `contracts/openapi.json` — попадёт
  в него вместе с остальными driver-эндпоинтами в T5.3.

## Раздел «Водители» в панели (T5.1a)
`src/admin/routes/drivers/page.tsx` — очередь заявок, `routes/drivers/[id]/page.tsx` — карточка;
мутации — `hooks/use-driver-moderation.ts`, диалог причины — `components/block-driver-prompt.tsx`,
DTO и карта статусов — `lib/driver.ts`. Вид — идиома списков ядра (эталон `routes/companies`).

- Экран открывается сразу очередью на проверку: чип «Ожидает проверки» предустановлен, потому что
  работа продавца здесь — разбор новых заявок, а допущенные и заблокированные это справочник.
- Порядок FIFO задаёт сервер, поэтому меню сортировки на экране НЕТ: колонок для сортировки
  список не принимает, а неработающий контрол хуже отсутствующего.
- «Допустить» у незаполненного профиля не показывается (сервер такую заявку отклонит), а карточка
  объясняет, чего не хватает.
- Номер телефона всюду человекочитаемый (`lib/phone.ts`), и поиск принимает его в том же виде:
  продавец копирует номер со своего же экрана.
