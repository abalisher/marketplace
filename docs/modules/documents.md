# Модуль `documents` — автогенерация документов

**Статус:** ГОТОВ (4/4 подзадачи) · **Код:** `backend/src/modules/documents/` (модель/сервис/шрифты) +
`backend/src/workflows/` (issue-order-document + update-document-settings + шаги + рендерер) +
`backend/src/subscribers/` (автовыпуск) + `backend/src/api/{store,admin}/orders/[id]/documents/` (ЛК/админ/экспорт) +
`backend/src/api/admin/document-settings/` (реквизиты) + `backend/src/admin/` (Settings-страница + widget заказа).

## Назначение
Автоматическое формирование документов-оснований по событиям заказа (счёт, накладная,
внутренний АВР) и их хранение с версионностью. Документы видны в ЛК обеих сторон
(покупатель + продавец/админ).

## Что закрывает ядро / что кастом
- **Хранение файла** — File Module ядра (`Modules.FILE`, локальный провайдер пишет в `static/`,
  в проде — S3/совместимый). Модуль documents хранит только МЕТАданные документа и ссылку `file_id`.
- **Рендер PDF** — кастом: `pdfkit` (чистый JS, без Chromium). Кириллица — встраиванием TTF-шрифта
  (стандартные шрифты PDF латиница-only). Рендер и связывание с File Module — в workflow-шаге
  (подзадача 2), не в сервисе модуля (модуль изолирован, File Module — другой модуль).
- **Нумерация, версионность, снапшот** — кастом, в сервисе модуля.

## Модели
- `Document` — строка документа: `type` (invoice|waybill|internal_avr), `order_id` (опазная ссылка
  на заказ ядра, не FK), `number` (человекочитаемый, INV-2026-000001), `version`, `is_latest`,
  `file_id`/`file_url` (ссылка на PDF в File Module; null пока не отрендерен), `snapshot` (json —
  замороженные исходные данные), `total_money`/`total_bonus` (суммы деньгами/бонусами раздельно —
  ТЗ 4.10), `currency_code`, `visible_to_buyer`/`visible_to_seller`, `note`.
- `DocumentSetting` — singleton реквизитов продавца для рендера (name/bin/address/bank/iban/footer);
  `getOrCreateSettings` создаёт с дефолтами. Идиома `BonusConfig`.
- `DocumentSequence` — счётчик номеров по ключу `<type>:<year>` (строка на тип/год).

### Почему `order_id` колонкой, а не module link
В order-lifecycle/bonus связь с заказом — забота workflow через link (сервис модуля заказ не знает).
В documents заказ нужен САМОМУ сервису: `issueDocument` группирует по `(order_id, type)` для
нумерации и версионности — это внутренняя логика домена. Поэтому храним заказ опазной ссылкой-колонкой
(без FK, без импорта модуля order — правило изоляции соблюдено). Выборка документов заказа для ЛК/админки
(подзадача 3) — прямым запросом `query.graph(entity:"document", filters:{order_id})`, link не нужен.
Link можно добавить позже, если понадобится graph-обход `order → documents` одним запросом.

## Сервис (подзадача 1 — готово)
- `getOrCreateSettings()` — singleton реквизитов.
- `nextDocumentNumber(type, now?)` — следующий номер из последовательности `<type>:<year>`
  (read-modify-write без блокировки; MVP-конкуренция низкая — документы формируются в workflow заказа).
- `issueDocument({order_id, type, snapshot, total_money?, total_bonus?, …})` — выпуск с версионностью:
  первая версия получает свежий номер; при наличии текущей версии по (order_id, type) — снимает с неё
  `is_latest`, новая версия = `version+1` с ТЕМ ЖЕ номером (переиздание — новая версия того же документа).
  `file_id` пуст (PDF рендерится позже).
- `attachRenderedFile({document_id, file_id, file_url})` — прикрепить отрендеренный PDF.

## Бизнес-правила (из ТЗ 4.10)
- Счёт на оплату — автоматически сразу после оформления заказа, покупателю (ЛК + email/push позже).
- Накладная — при отгрузке; при частичной отгрузке — на отгруженную часть.
- Внутренний АВР для юрлиц — информационный документ платформы (НЕ официальный). **На MVP не
  выпускается:** юрлица заморожены флагом `FEATURE_COMPANIES` (T10.9), и подписчик `order-invoice.ts`
  выходит до проверки связки company↔order. Тип документа, шаблон и нумерация не тронуты —
  включение флага возвращает выпуск. Покупателю-физлицу остаются счёт и накладная.
- Официальные АВР/ЭСФ — бухгалтер вручную на kgd.gov.kz; платформа даёт экспорт исходных данных
  заказа (API/выгрузка) — вне периметра автоматизации MVP.
- Суммы «деньгами» и «бонусами» — раздельно (данные из `bonus`).
- Хранение: у обеих сторон, с версионностью и историей.

## T4.9 (2026-08-13) — выпуск руками, обязательные реквизиты, реестр

Фокус-группа панели (T4.6) нашла: по заказу счёт не выпущен и кнопки нет, реквизиты продавца
пустые («Marketplace»), реестра документов нет. Изменения:

- **Реквизиты обязательны.** `requisites.ts` — чистая проверка полноты (наименование, БИН, адрес,
  банк, БИК, IBAN; дефолт модели «Marketplace» считается незаполненным). Проверка выполняется
  **в шаге `build-order-document-snapshot`**, а не отдельным шагом-guard'ом: шаг без связи по
  данным движок волен выполнить параллельно, и его отказ выпуск НЕ останавливает (проверено на
  стенде). Подписчики автовыпуска (`order-invoice`, `order-waybill`) проверяют то же самое ДО
  запуска workflow и пропускают заказ с предупреждением в лог — иначе каждый заказ сыпал бы
  ошибкой. Список полей продублирован в `admin/lib/documents.ts` (браузерный бандл не может
  импортировать код модуля).
- **Ручной выпуск** — `POST /admin/orders/:id/documents` `{type}`: повторный выпуск = новая версия
  того же номера (переиздание после правки реквизитов). Внутренний АВР — только по заказам юрлиц.
- **Отметка «отправлен покупателю»** — поле `Document.sent_to_buyer_at` (миграция
  `Migration20260813090000`), `POST /admin/documents/:id/mark-sent` через workflow с компенсацией.
  Канал отправки не выбран (развилка №0 владельцу), поэтому отметку ставит человек.
- **Реестр** — `GET /admin/documents`: текущие версии, счётчики по типам для чипов, фильтр
  `sent=sent|unsent`, поиск по номеру документа И по номеру/почте заказа (заказы — в другом модуле,
  их id дочитываются вторым запросом, см. `api/admin/documents/rows.ts`), в строке — заказ и
  плательщик человекочитаемо. Экран — `admin/routes/documents/`.
- **Покупатель в снапшоте**: название и БИН компании для юрлиц, имя из адреса для физлиц, адрес,
  телефон, email (раньше — только email).
- **Итог документа = итог заказа.** `retrieveOrder` с явным списком relations считает `total` БЕЗ
  доставки (счёт №24 занижался на 2 000 ₸ — тот же класс дефекта, что в T4.2a с `query.graph`).
  Итог берём выборкой `listOrders({select:["id","total"]})`, доставка встаёт отдельной строкой
  документа, поэтому сумма позиций сходится с итогом.
- **Мок-реквизиты** заполняет `seed-kz.ts` (решение владельца 2026-08-11: MVP на заглушках,
  реальные подставляются в настройках без правки кода). Заполняются только пустые поля.

## Бланки документов (2026-09-06)

Замечание владельца: «вид документов как черновик… у нас два одинаковых документа». Так и было —
`render-document-pdf.ts` печатал все три типа ОДНИМ макетом (абзацы текста + одна тонкая линия
над итогом), различалась только строка заголовка. Разобрано на три бланка, каждый по своему
образцу; ресерч форм — DECISIONS 2026-09-06.

- **Накладная** — форма **З-2** «Накладная на отпуск запасов на сторону» (приложение 26 к приказу
  Министра финансов РК от 20.12.2012 № 562, с изм. 19.08.2013): угловой штамп с реквизитами приказа,
  поле «Организация (индивидуальный предприниматель)», табличка «Номер документа | Дата
  составления», отправитель/получатель/ответственный за поставку, транспортная организация и
  доверенность (пустые линии — заполняются от руки), девять утверждённых граф (включая
  «Номенклатурный номер», «Количество подлежит отпуску» и «Количество отпущено»), «всего отпущено
  … наименований на сумму прописью», подписи «Отпустил / Главный бухгалтер / Получил», приписка о
  двух экземплярах. Единственная форма из трёх, которая утверждена законом.
- **Счёт** — утверждённой формы в РК НЕТ, требование одно: набор реквизитов, по которым банк
  проведёт платёж. Поэтому бланк двуликий, ветка выбирается по `buyer.is_company`:
  - **физлицу** (покупатель MVP) — расчётный документ магазина: шапка магазина, покупатель/телефон/
    адрес, позиции с единицами, итоги, сумма прописью, штамп **«ОПЛАЧЕНО»** с провайдером и датой.
    Счёт физлицу выпускается ПОСЛЕ оплаты Kaspi, поэтому банковской рамки и подписей на нём нет, а
    подвал прямо говорит, что фискальный чек приходит из банка;
  - **юрлицу** — классический казахстанский счёт: рамка «образец платёжного поручения»
    (Бенефициар / БИН / ИИК / Кбе / Банк бенефициара / БИК / Назначение платежа / КНП), поставщик,
    покупатель, договор, артикулы в таблице, «оплата означает согласие», срок действия счёта,
    подписи исполнителя и руководителя, место печати. Юрлица заморожены `FEATURE_COMPANIES` — бланк
    готов заранее.
- **Внутренний АВР** — двусторонний акт: исполнитель/заказчик, таблица работ, фраза «претензий не
  имеет», подписи обеих сторон с М.П. и явная приписка, что документ не официальный.

Устройство кода: `workflows/utils/render-document-pdf.ts` — только диспетчер (страница, шрифты,
выбор шаблона по типу); разметка — `workflows/utils/documents/render-{invoice,waybill,act}.ts`;
общие примитивы бланка (линованное поле, рамка реквизитов, таблица со сплошной сеткой, подписи,
угловой штамп, место печати) — `documents/document-canvas.ts`; форматирование сумм/дат/единиц —
`documents/document-format.ts`; типы снапшота — `documents/document-snapshot.ts`.
**Сумма прописью** — `src/lib/format/amount-in-words.ts` (без Intl: склонения «тенге/тиын» и
женский род тысяч ICU не даёт; «тиын» в бланках РК не склоняют).

Что доехало до снапшота ради бланков: **единица измерения** позиции (из `ProductCard.unit` по link
product↔product_card — без неё в графе «Ед. изм.» формы З-2 пустота), **артикул** варианта
(«номенклатурный номер»), **факт оплаты** (`payment.paid/provider/captured_at` — читается графом из
payment_collections) и три поля реквизитов: `seller_kbe` (Кбе, дефолт 17), `seller_knp` (КНП, дефолт
710) и `director_name` (расшифровка подписи), миграция `Migration20260906120000`. Все поля
снапшота опциональны — документы, выпущенные до правки, рендерятся тем же кодом.

**НДС:** продавец на MVP не плательщик, в бланках стоит «НДС: не облагается» и нули в графе «Сумма
НДС». Статуса плательщика НДС в реквизитах нет — появится вместе со ставкой, когда понадобится.

**Образцы бланков** для гейта U собирает юнит-тест: `DOC_PREVIEW_DIR=<путь> npx cross-env
TEST_TYPE=unit jest src/workflows/utils/documents` кладёт туда четыре PDF (счёт физлицу, счёт
юрлицу, накладная, акт) на демо-данных; без переменной тест просто проверяет, что PDF валиден и
бланки различаются.
