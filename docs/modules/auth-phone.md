# Модуль `auth-phone` — вход покупателя по номеру телефона (OTP)

**Статус:** реализован (T10.7, 2026-08-26).
**Код:** `backend/src/modules/auth-phone/` (провайдер аутентификации),
`backend/src/workflows/{request-phone-otp,verify-phone-otp}.ts` + шаги
`steps/{issue-phone-otp,verify-phone-otp,issue-customer-session}.ts`,
роуты `backend/src/api/store/auth/phone/*`, регистрация провайдера — `medusa-config.ts`.

## Назначение
Основной вход покупателя — **номер телефона + одноразовый код** (решение владельца 2026-08-25,
DECISIONS). Email/пароль остаётся только у учёток, заведённых раньше, и у панели (админ/продавец):
провайдер `emailpass` продолжает работать рядом. Профиль покупателя на MVP — **телефон + ФИО +
адрес**, больше при входе ничего не спрашиваем.

## Что закрывает ядро Medusa (не переизобретаем)
- **Auth-модуль** (`Modules.AUTH`): `auth_identity` (учётная сущность) + `provider_identity`
  (`provider`, `entity_id`, `provider_metadata`) и связь с покупателем через
  `auth_identity.app_metadata.customer_id`.
- **Аутентификация запросов**: middleware `authenticate("customer", ["session", "bearer"])` —
  наш токен принимается им как ядровый (полезная нагрузка = auth-context ядра).
- **Покупатель**: модуль `Modules.CUSTOMER` и ядровые шаги `createCustomersStep`,
  `setAuthAppMetadataStep`.

Своих моделей и таблиц у модуля НЕТ: состояние кода живёт в `provider_metadata`
провайдер-идентичности, учётка — ядровая.

## Границы
| Что | Где |
|---|---|
| Проверка кода | провайдер `phone` (`service.ts`), метод `authenticate` |
| Выдача кода, паузы | шаг `issue-phone-otp` (у него есть CRUD auth-модуля) |
| Учётка покупателя, токен | workflow `verify-phone-otp` |
| Канон номера | `normalize-phone.ts` (единственный ключ учётки) |
| Срок жизни/лимиты/dev-канал | `config.ts` (опции провайдера → env → умолчания) |

Почему выдача кода не в провайдере: интерфейс `AbstractAuthModuleProvider` рассчитан на один шаг
«данные → успех», а у нас два (запрос кода и его проверка). Если бы «запрос кода» жил в
`register`/`authenticate`, ядровые роуты `/auth/customer/phone[/register]` выдавали бы токен по
одному номеру телефона. Поэтому `register`/`update` у провайдера закрыты, а запрос кода идёт
нашим роутом.

## Номер телефона
Канон — `+7XXXXXXXXXX`. На вход принимается любая человеческая запись (`8 701 234-56-78`,
`+7 (701) 234 56 78`, `7012345678`); принимаются только **мобильные Казахстана** (код оператора
`70X`, `74X`, `75X`, `76X`, `77X`) — на городской номер SMS не придёт. Номер — ключ
провайдер-идентичности (`entity_id`), поэтому вид должен быть однозначным.

## Код входа
- Живёт в `provider_metadata` провайдер-идентичности: `code_hash` (SHA-256 от `номер:код`),
  `code_expires_at`, `code_requested_at`, `attempts`.
- Срок жизни — `PHONE_OTP_TTL_SECONDS` (по умолчанию 300 с), длина — `PHONE_OTP_CODE_LENGTH` (6).
- Неверных попыток на код — `PHONE_OTP_MAX_ATTEMPTS` (5); на последней код **аннулируется**
  (даже верный код после этого не подходит — нужен новый).
- Пауза перед повторной отправкой — `PHONE_OTP_RESEND_SECONDS` (60 с); раньше — ответ 429 с
  `retry_after` (кнопка «выслать снова» с таймером).
- **Dev-канал** (`PHONE_OTP_DEV_CHANNEL`, по умолчанию включён вне production): SMS-провайдера
  на MVP нет (гейт В у владельца), поэтому код пишется в лог бэкенда и приходит полем `dev_code`
  в ответе на запрос кода; в этом же режиме он лежит открытым текстом в `provider_metadata`
  (`dev_code`) — так его видно в панели. В production dev-канал выключен, и до подключения
  SMS-провайдера вход по номеру там работать не будет.

## API
| Роут | Что делает |
|---|---|
| `POST /store/auth/phone/otp` | запрос кода: `{ phone }` → `{ phone, expires_in, resend_after, dev_code }`; 400 — не мобильный номер, 429 — пауза |
| `POST /store/auth/phone/verify` | подтверждение: `{ phone, code }` → `{ token, customer, created }`; 401 — `invalid_code`/`code_expired`, 429 — `too_many_attempts` |

Оба роута публичные (это и есть вход) и требуют `x-publishable-api-key`, как все `/store/*`.
Ответ на запрос кода одинаков для нового и известного номера — по нему нельзя узнать,
зарегистрирован ли покупатель. Токен — обычный Bearer покупателя (`actor_id`, `actor_type`,
`auth_identity_id`, `app_metadata.customer_id`), срок — `jwtExpiresIn` проекта.

## Вход и регистрация — один путь
`verify-phone-otp`:
1. код верен → покупатель уже связан с номером (`app_metadata.customer_id`) → сессия;
2. иначе ищем покупателя с этим номером и `has_account` (учётка, заведённая раньше по email или в
   панели) → **связываем**, а не дублируем: владение номером подтверждено кодом;
3. иначе создаём покупателя с профилем «только телефон» (`created: true`) — ФИО и адрес спрашиваются
   один раз при оформлении (T10.8: их собирает и сохраняет в профиль инструмент `set_delivery`
   ассистента; email не спрашиваем вовсе — на корзину идёт служебный `<цифры номера>@phone.invalid`,
   см. DECISIONS 2026-08-26).

Ядровый `createCustomerAccountWorkflow` не используется: он требует email, а его в профиле MVP нет.

## Открытые вопросы (гейты)
- **Гейт В:** SMS-провайдер (Mobizon/SMSC/оператор) — до его выбора боевой канал доставки кода
  отсутствует, стенд живёт на dev-канале.
- Ограничение частоты по IP (не только по номеру) — за MVP; сейчас защита от перебора кода
  строится на лимите попыток и коротком сроке жизни.
