# Модуль `assembly` — сборка заказа по категориям

**Статус:** реализован (T10.11, 2026-09-01) · **Код:** `backend/src/modules/assembly/` (модели, сервис,
чистый распад `split.ts`, роли сборщиков `roles.ts`, миграция), workflows
`backend/src/workflows/{split-order-assembly,start-assembly-task,mark-assembly-item,complete-assembly-task}`
+ шаги `steps/{resolve-order-assembly-lines,create-assembly-tasks,start-assembly-task,mark-assembly-item,
complete-assembly-task,summarize-order-assembly,ensure-order-assembling}`, подписчики
`subscribers/{order-assembly-split,assembly-shortage}`, admin API `backend/src/api/admin/assembly-tasks/`
и `backend/src/api/admin/orders/[id]/assembly/`, очередь отгрузки — `backend/src/api/admin/shipping-queue/`,
приложение сборщика — `mobile/apps/partner/lib/features/assembly/`, экран панели — `backend/src/admin/routes/shipping/page.tsx` (+ `components/shipping-order-row.tsx`,
`lib/shipping.ts`, `styles/shipping.css`), учётки сборщиков — `src/scripts/create-picker-users.ts`.

## Назначение
Недостающее звено между «оплачено» и «выдано водителю» (решение владельца 2026-08-25, пп. 4–5).
Оплаченный заказ автоматически распадается на **задания сборки** — по одному на каждую присутствующую
в заказе категорию каталога (`finishing` / `electrical` / `plumbing` / `fasteners`, см. T10.10).
Каждое задание собирает своя группа: **группа = категория**. Заказ считается СОБРАН, когда собраны
все задания; нехватка позиции поднимает флаг отвечающему за отгрузку, а не блокирует заказ молча.

## Границы: что берём у ядра и у соседних модулей
- **Физика сборки — ядро:** `createOrderFulfillmentWorkflow` (уже обёрнут в `complete-order-assembly`).
  Задания сборки его НЕ заменяют: они — работа людей на складе, fulfillment — факт для ядра.
- **Бизнес-статус заказа — `order-lifecycle`:** `assembling` / `partially_assembled` / `assembled`
  остаются там же и меняются тем же workflow. Модуль `assembly` их не дублирует и не импортирует
  соседний модуль напрямую — только через workflow (правило изоляции).
- **Категория — ядровая `product_category`** (источник правды `src/lib/catalog/categories.ts`).
  В задании хранится `category_handle` (стабильный ключ = группа) и `category_name` (снапшот имени
  на момент распада: владелец вправе переименовать категорию, история сборки меняться не должна).

## Модели
`backend/src/modules/assembly/models/`:
- **`AssemblyTask`** — задание на одну категорию одного заказа: `order_id` (опазная ссылка-колонка,
  не FK — идиома `logistics.trip_stop`), `category_handle`, `category_name`, `status`,
  `assignee_id` (кто взял), `started_at`, `completed_at`, `completed_by` (кто отметил), `note`.
  **Уникальный индекс `(order_id, category_handle)` среди живых строк** — на категорию заказа ровно
  одно задание даже при двойной доставке события.
- **`AssemblyTaskItem`** — позиция задания: `order_item_id`/`variant_id` (опазные ссылки),
  снапшот `title`/`sku`, `quantity` (сколько надо), `picked_quantity` (сколько набрано),
  `status`, `marked_at`, `marked_by`, `note`.

Статусы (`models/constants.ts`):
- задание — `pending` (ожидает) → `picking` (собирается) → `assembled` (собрано) | `shortage` (нехватка);
  `shortage → picking` разрешён: довезли позицию — сборщик возвращается и закрывает задание;
- позиция — `pending` → `picked` (набрана целиком) | `partial` (набрана частично) | `missing` (нет в наличии).

## Стейт-машина и чистые правила (сервис)
Всё, что можно проверить без БД, — чистые функции сервиса (юнит-тесты
`__tests__/assembly-rules.unit.spec.ts`):
- `assertAssemblyTaskTransition(from, to)` — карта переходов задания;
- `resolveItemMark({status, quantity, picked_quantity})` — согласование количества со статусом
  («набрано» = всё, «нет в наличии» = 0, «частично» — строго от 1 до quantity−1);
- `assertAllItemsMarked(items)` — задание не закрыть, пока по каждой позиции нет отметки
  (иначе «пропустил» и «нет в наличии» на экране отгрузки неразличимы);
- `deriveTaskCompletion(items)` — итог задания: всё набрано → `assembled`, иначе `shortage`;
- `summarizeOrderAssembly(tasks)` — агрегат заказа: `is_finished` (по всем заданиям отработали),
  `is_assembled` (заказ СОБРАН), `has_shortage` (флаг отгрузке);
- `fulfillmentLinesFromTasks(tasks)` — что реально набрано, для ядрового fulfillment;
- `splitOrderLinesByCategory(lines)` (`split.ts`) — сам распад: одно задание на категорию, позиции
  делятся без остатка, порядок заданий — канонический порядок четырёх категорий.

## Сценарии (workflows)
- **`split-order-assembly`** — распад. Запускается подписчиком `order-assembly-split` на ядровом
  `order.placed`: у нас 100% предоплата (`place-order` пропускает только оплаченную корзину), значит
  «размещён» = «оплачен». Задания — вторичный артефакт (идиома счёта в `order-invoice`): их создание
  в подписчике, а не внутри `place-order`, чтобы сбой распада не откатывал оплаченный заказ.
  Идемпотентно: повторный прогон ничего не создаёт и события не шлёт.
- **`start-assembly-task`** — сборщик взял задание (`pending → picking`).
- **`mark-assembly-item`** — отметка по одной позиции (отдельный workflow: экран телефона отмечает
  позиции по одной, каждая отметка откатывается самостоятельно).
- **`complete-assembly-task`** — сборщик закрыл задание. Дальше решает агрегат по заказу: когда
  закрыто ПОСЛЕДНЕЕ задание, шаг `ensure-order-assembling` догоняет жизненный цикл
  (`new → confirmed → assembling` от имени системы), а `complete-order-assembly` создаёт ядровый
  fulfillment на реально набранное → статус заказа `assembled` (всё собрано) или
  `partially_assembled` (была нехватка).

## События
`modules/assembly/events.ts`, namespace `assembly.*` (своих `order.*` не эмитим — их шлёт ядро):
- `assembly.tasks_created` — заказ разложен на задания;
- `assembly.shortage_reported` — задание закрыто с нехваткой; подписчик `assembly-shortage` пока
  логирует (канал уведомлений в MVP не заводим — развилка №0), флаг живёт в данных заказа;
- `assembly.order_finished` — по всем заданиям заказа сборщики отработали.

## Роли-группы сборщиков
Прав у admin-пользователей в OSS-ядре Medusa v2 нет, поэтому роль и группа живут в `user.metadata`
(идиома `create-seller-user.ts`): `role = "picker"`, `assembly_group = <handle категории>`.
Разбор — чистая функция `readPickerIdentity` (`roles.ts`). Учётки заводит
`npx medusa exec ./src/scripts/create-picker-users.ts` — по одной на категорию
(`picker.<handle>@stroymarket.kz`, пароль из `PICKER_PASSWORD`).

## API (admin)
- `GET /admin/assembly-tasks` — очередь заданий: фильтры `status` (одно значение или список),
  `category`, `order_id`, пагинация, счётчики по статусам для чипов. **Один ресурс на два экрана:**
  сборщику категория подставляется из его учётки и перекрывает присланную (задания чужой группы он
  не видит; сборщик без группы получает пустую очередь), отгрузка видит все задания.
- `GET /admin/assembly-tasks/:id` — карточка задания с позициями.
- `POST /admin/assembly-tasks/:id/start` — взять задание.
- `POST /admin/assembly-tasks/:id/items/:item_id` — отметка по позиции; в ответ — всё задание
  целиком (экран телефона перерисовывает список одним ответом).
- `POST /admin/assembly-tasks/:id/complete` — закрыть задание; в ответе задание и агрегат заказа.
- `GET /admin/orders/:id/assembly` — сборка одного заказа: плитки категорий + агрегат.
- `GET /admin/shipping-queue` — очередь ЭКРАНА ОТГРУЗКИ (T10.13): заказы, которые ещё не уехали, —
  строка заказа (покупатель, адрес, сумма), плитки категорий, стадия, счётчики стадий и готовая цель
  перехода «передать водителю» (`ship_target`). Фильтр `stage`, пагинация.

Строку экрана собирает `api/admin/assembly-tasks/rows.ts` (роуты тонкие), контракт —
фрагмент `assembly-tasks.oas.json` (схемы `AdminAssemblyTask*`, `AdminOrderAssembly*`).

## Экран отгрузки (T10.13)
`/app/shipping` — рабочий стол отвечающего за отгрузку: очередь заказов до отправки, у каждого
плитки категорий (статус, кто собирает, сколько позиций отмечено, где нехватка), стадия одним
бейджем и кнопка **«Отгрузить»** (до 2026-09-04 — «Передать водителю»: на показе доставка
диспетчерская, водителя в сценарии нет). Клик по номеру заказа открывает карточку drawer'ом —
очередь не теряет фильтр и место.

Решения экрана:
- **Стадия считается по заданиям, а не по статусу заказа.** Жизненный цикл догоняет факт сборки
  только при закрытии ПОСЛЕДНЕГО задания (`ensure-order-assembling`), поэтому заказ, который сборщики
  уже разбирают, висит ещё в `new`/`confirmed`. Фильтр по статусу заказа прятал бы из очереди именно
  то, что отгрузке нужнее всего. Стадии три: `assembling` (не по всем заданиям отработали) →
  `ready` (собрано всё) | `shortage` (отработали, но часть не набралась).
- **Очередь читается до потолка `SHIPPING_QUEUE_SCAN_CAP` (200 заказов) и режется на страницы в
  памяти.** Стадию нельзя спросить у БД фильтром, а врать в счётчиках чипов нельзя; заказов «до
  отгрузки» в работе — десятки. Если очередь упёрлась в потолок, экран говорит это подписью, а не
  прячет остаток молча.
- **Цель перехода приходит с сервера готовой** (`ship_target`): fulfillment под отгрузку +
  **реально набранные** позиции (`fulfillmentLinesFromTasks`), а не все позиции заказа — у частично
  собранного заказа ядровый fulfillment создан именно на набранное. Экран возвращает цель обратно как
  есть, технических id не показывает.
- **Нехватка не блокирует кнопку.** Стейт-машина разрешает `partially_assembled → in_delivery`;
  экран называет категории с нехваткой и оставляет решение человеку (требование владельца, п. 4).
- **Не `DataTable`.** У строки очереди нет одной высоты — в ней от одной до четырёх плиток; список
  карточек читается лучше таблицы со вложенной сеткой (идиома панелей дашборда). Чипы со счётчиками,
  порядок FIFO и пагинация — как в очереди заказов.
- Fulfillment'ы читаются через `query.graph`, а НЕ `relations: ["fulfillments"]` у сервиса модуля
  order: связь кросс-модульная, у сервиса поле пустует (нашлось http-тестом — цель отгрузки выходила
  `null` у собранного заказа).

## Приложение сборщика (T10.12)
`mobile/apps/partner` — роль «сборщик» внутри приложения персонала (решение владельца по развилке
№7 от 2026-09-02: четвёртое приложение и четвёртая сборка не заводятся). Экраны: вход сотрудника →
«мои задания» → задание → отметки по позициям → «Собрано». Данные — те же admin-роуты
`/admin/assembly-tasks`: у сборщика категория подставляется из учётки, так что «мои задания» и
«вся очередь» — один и тот же ресурс.

Решения приложения:
- **Актор `user`, а не `customer`.** Вход — `/auth/user/emailpass` (учётка панели), сессия хранится
  отдельным ключом от покупательской (`SecureStaffSessionStore`): на одном устройстве это разные
  токены, общий ключ выкидывал бы покупателя. Слой авторизации сотрудника лежит в `packages/core`
  (`staff_*`) — им же будут пользоваться роли продавца и водителя.
- **Профиль сотрудника не запрашивается**: `/admin/users/me` в контракте нет. Кто вошёл — email из
  хранилища сессии; какая у него категория — поле `group` в ответе очереди (его подставляет сервер).
- **Отметки переживают потерю сети.** Отметка, не дошедшая до сервера, ложится в очередь на
  устройстве (`PendingMarkStore` поверх shared_preferences) и накладывается на задание при показе —
  сборщик видит свою работу и прогресс «отмечено N из M» до отправки. По паре «задание + позиция»
  хранится только последнее решение; отправка идёт в порядке очереди; отказ сервера (задание успели
  закрыть) отбрасывает ровно эту отметку, обрыв связи — останавливает отправку и сохраняет остаток.
  Правила — чистые функции `pending_mark_rules.dart`, покрыты юнитом.
- **Закрыть задание без сети нельзя** (`MarksNotSentException`): итог задания сервер выводит из
  отметок, а закрытие с неполной картиной дало бы неправильный итог. Кнопка сначала досылает
  очередь, и только потом закрывает.
- **Что нельзя, то не показываем**: кнопки отметок появляются только у задания в работе (сервер
  отметку у `pending` и не примет), «Собрано» разблокируется, когда отмечены все позиции.
- **Категория чужой группы недостижима из интерфейса вовсе** — фильтра по категории на экране нет.
