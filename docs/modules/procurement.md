# Модуль `procurement` — закуп материалов, себестоимость, приход на склад

**Статус:** реализация — подзадачи 1a (модуль) + 1b (workflow+admin API) + 1c (seller-first admin-UI) + 2
(ИИ-приёмка накладной, Gemini Flash Lite) ГОТОВЫ (2026-07-22/23) + 3 (себестоимость и наценка на карточке
товара, T4.9a) ГОТОВА (2026-09-03); границы MVP согласованы владельцем (FIFO по партиям). Ручной И ИИ-приход накладной закрыты end-to-end (модель → workflow → admin-UI → Gemini). Введён
пивотом 2026-07-22 (DECISIONS, решения 6–7); провайдер ИИ — **Gemini** (решение владельца 2026-07-23, не Claude).
**Код (план):** `backend/src/modules/procurement/` + workflows `backend/src/workflows/` + admin API `backend/src/api/admin/procurement/`.

## Назначение
Buy-side продавца: у кого, когда, по какой цене и в каком количестве закуплены материалы; оприходование закупа
на склад; хранение себестоимости для расчёта маржи. **Себестоимость и данные закупа НЕ видны покупателю**
(DOMAIN «учёт закупа… не виден покупателю»). Точка входа для ИИ-приёмки (накладная/фото → приход).

## Что закрывает ядро / что кастом
- **Ядро `inventory`** уже есть: `InventoryItem` (привязан к variant), `InventoryLevel` per location
  (`stocked_quantity`). Увеличение остатка при приходе = корректировка inventory level — делаем ЧЕРЕЗ ядро (workflow),
  не своя таблица остатков.
- **Ядро НЕ имеет** понятий поставщика, прихода/накладной закупа, себестоимости/COGS, партий — это всё кастом.
- **Кастом (`procurement`):** реестр поставщиков, документ прихода (накладная закупа) со строками, себестоимость
  на уровне строки/варианта, оприходование (проводка → inventory ядра). Модуль не импортирует ядро/другие модули
  напрямую — только через workflows и опазные ссылки-колонки (`variant_id`/`location_id`/`file_id`), как в logistics.

## Модели (предложение)
- `Supplier` — поставщик (lean): `name`, `bin` (опц., БИН/ИИН), `contact_phone`/`contact_email` (опц.), `note`, `active`.
  Ровно чтобы атрибутировать приход. Без договоров/долгов/платежей на MVP.
- `Receipt` — приход (накладная закупа): `supplier_id` (опазная ссылка, опц.), `location_id` (склад; по пивоту один,
  колонка — на будущее), `reference` (номер накладной поставщика), `received_at`, `status` (`draft`|`posted`),
  `source` (`manual`|`invoice_ai`|`photo_ai` — для ИИ-приёмки), `document_file_id` (скан накладной, опц.),
  `total_cost` (сумма по строкам), `note`. hasMany `lines`.
- `ReceiptLine` — строка прихода: `receipt` (belongsTo), `variant_id` (опазная ссылка на variant ядра; NULL пока
  не сопоставлено с SKU — важно для ИИ-черновика), `recognized_title`/`material_kind` (что распознали до маппинга),
  `quantity`, `unit`, `unit_cost`, `line_cost`. Себестоимость живёт здесь.
- `Batch` — партия закупа (РЕШЕНИЕ ВЛАДЕЛЬЦА 2026-07-22: FIFO по партиям): `variant_id` (опазная ссылка),
  `receipt_line` (belongsTo), `quantity_received`, `quantity_remaining`, `unit_cost`, `received_at`,
  `expires_at` (опц., срок годности — цемент и т.п.). Каждая проводка строки прихода порождает партию;
  списание при продаже идёт по FIFO (самая ранняя `received_at` с `quantity_remaining > 0`).

## Модель себестоимости
**FIFO по партиям (`Batch`)** — решение владельца 2026-07-22. Каждый приход строки создаёт партию со своей
`unit_cost` и `quantity_remaining`. Себестоимость проданного = списание слоёв партий по FIFO (от самой ранней).
Себестоимость текущего остатка = Σ(`quantity_remaining` × `unit_cost`) по открытым партиям. Даёт точную маржу и
учёт срока годности. Чистая функция `consumeFifo(batches, qty)` → {списанные слои с себестоимостью, обновлённые остатки}.
Средневзвешенная отвергнута владельцем (искажает маржу при колебании закуп-цен, нет срока годности).

## Проводка прихода (workflow, с компенсацией)
`post-receipt`: `Receipt.status: draft → posted` → для каждой строки с сопоставленным `variant_id`:
(1) увеличить `InventoryLevel.stocked_quantity` на складе через inventory ядра (шаг со снимком для отката);
(2) создать `Batch` (партию) с `quantity_received = quantity_remaining = qty`, `unit_cost`, `expires_at`.
Строки без `variant_id` блокируют проводку (сначала сопоставить SKU). Компенсация — откат остатка и удаление партии.
Списание партий по FIFO при продаже (интеграция с order/inventory) — отдельная подзадача (см. ниже). Идиома
upsert/компенсации — как в logistics/estimator.

## Границы MVP (НА РЕВЬЮ ВЛАДЕЛЬЦУ)
**В MVP:**
1. Реестр поставщиков (lean CRUD).
2. Ручной приход: поставщик + строки (SKU + кол-во + закуп-цена) → черновик → проводка (остаток ядра + партия).
3. Себестоимость по FIFO-партиям (`Batch`) + срок годности → точная маржа для отчёта.
4. **Seller-first admin-UI** (решение #8): список приходов + task-focused форма прихода в пару кликов (поставщик →
   строки с автокомплитом SKU → «Провести»). Без JSON/metadata/лишних полей.

**Отложить за MVP:**
- **ИИ-приёмка** (накладная OCR + фото → черновик прихода) — отдельная подзадача ПОВЕРХ ручного прихода (см. ниже).
- Списание FIFO-партий при ПРОДАЖЕ (интеграция с order/inventory) — чистая функция `consumeFifo` в MVP, применение
  к реальной продаже (workflow при отгрузке) — отдельная подзадача (нужен стабильный флоу отгрузки).
- Заказ поставщику (purchase order до прихода) — MVP фиксирует только факт прихода.
- Долги/платежи поставщикам, прочие расходы кроме товара (операционная «расходка»).
- Возврат поставщику.

## ИИ-приёмка (подзадача 2 — реализует DECISIONS-решение 7)
Поверх ручного прихода, на **Google Gemini Flash Lite** (решение владельца 2026-07-23 — не Claude; провайдер
через REST, без SDK — см. DECISIONS 2026-07-23):
- **Накладная (ГОТОВО 2026-07-23):** продавец грузит PDF/фото накладной (base64 в JSON, `POST /admin/procurement/
  parse-invoice`) → Gemini со structured output извлекает строки (наименование/кол-во/ед./цена в целых тенге) →
  фронт префиллит форму прихода (`source=invoice_ai`, строки с `recognized_title`, `variant_id` пустой) → продавец
  построчно сопоставляет SKU и сохраняет/проводит существующим флоу create-draft. Роут ничего не персистит
  (распознавание рекомендательное). Код: `src/lib/gemini.ts` (адаптер REST) + `src/lib/invoice-ai.ts`
  (схема/промпт/`sanitizeRecognizedInvoice`) + `src/api/admin/procurement/parse-invoice/route.ts`; фронт —
  `ReceiptCreateDrawer`. Ключ/модель — env (`GEMINI_API_KEY`|`GOOGLE_API_KEY`, `GEMINI_MODEL`). Live-прогон
  (smoke `src/scripts/smoke-invoice-ai.ts`) подтверждён 2026-07-23 на `gemini-3.5-flash-lite`.
- **Фото товара (ОТЛОЖЕНО):** фото мешка/паллеты → Gemini определяет вид → диалоговое уточнение количества
  («сколько мешков?») → строка (`source: photo_ai`) → сопоставление SKU → проводка. Многоходовой разговорный
  флоу — ляжет вместе с задачей (e) «разговорный ассистент» (переиспользует `src/lib/gemini.ts`).
Предел файла — 8 МБ (`MAX_INVOICE_BYTES` в `src/lib/invoice-ai.ts`): им ограничен и валидатор (в символах
base64), и проверка в drawer до чтения файла; лимит тела роута в `middlewares.ts` — 12 МБ, с запасом на
кодирование (без него снимок накладной падал с 413 ещё до валидатора).
Нечитаемый ввод → понятная ошибка + ручной ввод (идиома estimator). Результат распознавания — рекомендательный, редактируем.

## Решённые вопросы (владелец 2026-07-22)

2. **Роль себестоимости:** хранить + показать маржу продавцу; авто-ценообразование — позже (дефолт принят).
3. **Поставщик:** отдельная сущность `Supplier` (дефолт принят).
4. **Срок годности:** ✅ да — `Batch.expires_at` (следствие FIFO).
5. **Порядок:** ручной приход (подзадача 1) → ИИ-приёмка (подзадача 2) (дефолт принят).
