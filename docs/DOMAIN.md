  везёт клиенту, GPS виден покупателю. Пересматривает роль «Водитель» из раздела «Роли» (был сотрудник продавца).
- **Закуп/себестоимость** («Склады и остатки» → «Учёт закупа… НЕ виден покупателю») — теперь реализуется модулем `procurement`
  + ИИ-приёмка (накладная/фото → приход на склад).
- **UI — seller-first**, комфорт и минимум кликов; убрать служебный шум (JSON/metadata/лишние поля).

## Роли

**Платформа:** Суперадмин (назначает админов, тарифы, глобальные настройки) → Админ (модерация продавцов,
покупателей-юрлиц и карточек товара, мониторинг).

**Продавец** (на MVP — один, мультивендор в Фазе 2), внутренняя иерархия:
- Руководитель — дашборд-конструктор показателей, цены, все склады, структура сотрудников.
- Менеджер по заявкам — обработка заказов, частичное исполнение, коммуникация.
- Кладовщик — остатки конкретного склада, приём/отгрузка.
- Бухгалтер — АВР/ЭСФ на внешних порталах (kgd.gov.kz — ВНЕ периметра MVP), сверка; платформа даёт экспорт данных.
- Водитель — приложение: рейсы, загрузка/отгрузка с фото/подписью, GPS-трекинг в реальном времени.

**Покупатель:** физлицо (самостоятельная регистрация) и юрлицо (регистрация + БИН + учредительные документы +
модерация админом до активации лимитов). У юрлица — свои сотрудники с лимитами заявок. RBAC на всех уровнях.

Авторизация: телефон/email + пароль, SMS-подтверждение, восстановление доступа.

## Каталог
- Единый справочник SKU; иерархия: категория → подкатегория → товар.
- Сегмент каждого товара: **эконом / комфорт / бизнес**.
- Карточка: наименование, код, категория, сегмент, ед. изм., фасовка/вес/объём (нужно логистике!), фото, характеристики, сертификаты.
- Модерация карточек: «На модерации» → «Одобрено» / «Отклонено (комментарий)». Изменение ключевых характеристик одобренной карточки → снова на модерацию. Сертификаты обязательны.

## Склады и остатки
- Модель: **Город → Склад (до 5 на город) → Остаток**. Верхний уровень не менять — заложен мультигород/мультивендор.
- Остатки покупателю — в реальном времени, в разрезе склада/города.
- Нет товара → автоматическое предложение альтернативы (категория/сегмент/характеристики).
- Учёт закупа продавца у своих поставщиков (приход, партия, себестоимость) — НЕ виден покупателю.
- Интеграционный API остатков/цен/документов для внешних учётных систем (1С).

## Заказ
Статусы: `Новый → Подтверждён → В сборке → Частично/Полностью собран → В доставке → Доставлен → Закрыт` (+ `Отменён`, `Возврат`).
Уведомления обеим сторонам на каждом переходе (push/SMS/email). Корзина — товары одного продавца (MVP).

**Сборка по категориям** (решение владельца 2026-08-25, пп. 4–5; реализовано T10.11): оплаченный
заказ автоматически распадается на **задания сборки** — по одному на каждую присутствующую в заказе
категорию каталога. Каждое задание собирает своя группа (**группа = категория**), сборщик работает с
телефона: берёт задание, отмечает позиции (набрано / частично / нет в наличии), закрывает. Заказ
**СОБРАН**, когда собраны все задания; закрытие последнего передаёт набранное в отгрузку. Нехватка
позиции не блокирует заказ молча — задание закрывается со статусом «нехватка», заказ становится
«частично собран», а флаг видит отвечающий за отгрузку и решает: ждать, заменить или везти как есть.
Стадия «Подтверждён» для предоплаченного заказа физлица проставляется системой в момент сборки —
менеджер её больше не нажимает.

**Частичное исполнение:** менеджер подтверждает частичную отгрузку → документы на отгруженную часть →
покупателю альтернатива или ожидание → оплата пересчитывается автоматически (для предоплаты — возврат/зачёт разницы).

**Способ получения и приёмка** (поправка 2026-07-15; ПЕРЕСМОТРЕНО пивотом 2026-07-22 — см. п. выше):
- **Доставка** транспортом продавца — **единственный способ**. Покупателя рядом с продавцом нет, поэтому
  приёмку подтверждает покупатель **кодом получения** (дублируется SMS): код = подпись о приёмке, не
  называть, пока товар не проверен. «Передан по коду» — не отдельный статус, а способ подтвердить «Доставлен».
- ~~Самовывоз у окна~~ и ~~Продажа у окна (POS)~~ — **сняты пивотом 2026-07-22**: всё через приложение с
  доставкой. Реализация удалена (см. `docs/modules/order.md` → «Способ получения»).

## Оплата
Сценарии (настраиваются на уровне заказа/договора): 100% предоплата · частичная предоплата (% настраиваемый) ·
постоплата/отсрочка (ТОЛЬКО юрлица, в рамках одобренного лимита) · онлайн — Kaspi Pay/QR (другие провайдеры — через единый шлюз).
Счета формирует платформа автоматически от имени продавца. Полные данные карт НЕ храним (PCI DSS на стороне эквайера).

## Ценообразование
Цены по позиции, опционально по складам. Ручная скидка на уровне заказа (MVP), персональные цены юрлицам — позже.
**История изменений цен — бессрочно**: кто, когда, старое/новое. Логируются также: статусы заказов, модерация, скидки, лимиты.

## Бонусы
1% от суммы заказа (настраиваемый: платформа/сегмент) начисляется после ЗАКРЫТИЯ заказа и истечения окна возврата.
Списание — частичная оплата будущих заказов, не более настраиваемого % от суммы нового заказа. Вывод денег — запрещён.
Опционально сгорание (настраиваемый срок) + уведомление. В документах суммы «деньгами» и «бонусами» — раздельно.

## Возвраты
Окно: **14 дней** с даты доставки, при сохранении товарного вида. Курьер при заборе — осмотр по чек-листу с фото в приложении.
Доставка возврата — за счёт покупателя (та же тарифная сетка). Деньги — на карту по регламенту эквайера, статус в ЛК.

## Скоринг (юрлица)
Критерии: история платежей (просрочки), количество/сумма заказов, возвраты/отмены, срок работы с платформой.
Определяет лимит отсрочки/кредита. Правила расчёта — НАСТРАИВАЕМЫЕ (админ/руководитель продавца), не хардкод.
Продавец видит карточку рейтинга перед одобрением отсрочки.

## Логистика
Способ получения — только **доставка** (пивот 2026-07-22, самовывоз снят; см. «Заказ»).
Доставка — транспортом продавца; стоимость по тарифной сетке (вес/объём/зона, настраивается продавцом).
GPS водителя в реальном времени — виден покупателю и диспетчеру на карте. Партнёрская логистика — Фаза 2.

## Документы
Автоматически: счёт (при оформлении заказа), накладная (при отгрузке/частичной отгрузке), внутренний АВР для юрлиц.
Официальные АВР/ЭСФ — бухгалтер вручную на госпорталах; платформа даёт выгрузку данных (API/экспорт).
Все документы — в ЛК обеих сторон, с версионностью.

## ИИ-модуль (estimator)
- Голосовой ввод: минимум русский и казахский (STT → структурированный запрос к каталогу/калькулятору).
- Расчёт материалов из файла проекта (PDF, DOC/DOCX, XLS/XLSX, JPEG/PNG): распознавание площадей/периметров/высот →
  расчёт по нормативной базе расхода (АДМИНИСТРИРУЕМЫЙ справочник, не хардкод) → результат помечен как рекомендательный, редактируем.
- Подборка в 3 вариантах по сегментам (эконом/комфорт/бизнес) с итогом по каждому; сегменты можно смешивать; учитывает остатки.
- Нечитаемый файл → понятная ошибка + ручной ввод параметров.

## Масштаб и производительность
MVP: 1 продавец, ~1 000 SKU, ~100 покупателей, до 10 заказов/день. Целевой рост ×10 без переработки:
пагинация везде, индексация по городу/складу, кэширование остатков.

## Монетизация
MVP: подписка продавца (тарифные планы). Заложить в архитектуру (не в UI): комиссия с транзакций, рекламный блок.

## Критерии приёмки MVP (сокращённо)
Самостоятельная регистрация (физ/юр) · каталог с реальными остатками · заказ + оплата + трекинг · мгновенное отражение
изменения цены/остатка + история цен · альтернативы и частичная отгрузка · автосчёт и накладная · модерация товара и юрлица ·
дашборд руководителя · бонус начислен и применён · estimator выдаёт расчёт по сегментам из загруженного файла.
