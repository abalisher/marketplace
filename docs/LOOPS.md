# Протокол агентных циклов (agentic loops)

Проект спроектирован под работу циклами: бэклог в `docs/PLAN.md` — эпики и таски-чекбоксы
с назначенными гейтами качества (`docs/QUALITY.md`), каждая итерация берёт ОДИН таск и доводит
его до проверенного состояния.

## Итерация цикла (обязательная последовательность)
1. Прочитать `docs/STATE.md` (сводка) → взять из `docs/PLAN.md` первый незакрытый таск активного эпика (`- [ ]`/`[~]`).
2. Если таск крупнее одной итерации — разбить его на подзадачи прямо в PLAN.md и взять первую.
3. Выполнить, соблюдая правила `CLAUDE.md` (изоляция: один модуль/пакет за итерацию).
4. **Верификация = гейты таска по `docs/QUALITY.md` — без них чекбокс не ставится**: гейт К (код) —
   всегда; гейты U (UI/UX) и Ф (фокус-группа) — если назначены в паспорте таска. Гейт В (владелец) —
   таск остаётся `[~]` с пометкой «ждёт ОК владельца», цикл идёт дальше.
5. Отметить статус в PLAN.md + строку результата гейтов; в STATE.md — строку в «Журнал», сдвинуть
   «Следующий шаг». Архитектурный выбор → `DECISIONS.md`. Изменён модуль → `docs/modules/<имя>.md`.
6. Заблокирован (нужны ключи/решение владельца)? НЕ останавливать цикл: записать блокер в
   «Известные проблемы» STATE.md / «Открытые развилки» PLAN.md и взять следующий таск.

## Типы циклов и когда какой использовать
(по официальному гайду: claude.com/blog/getting-started-with-loops)

| Тип | Запуск | Стоп-условие | Когда в этом проекте |
|---|---|---|---|
| Turn-based (обычная сессия) | «возьми следующий таск из PLAN.md» | таск выполнен, гейты пройдены | разовые задачи |
| Goal-based `/goal` | цель с ВЕРИФИЦИРУЕМЫМ критерием + лимит попыток | критерий достигнут или попытки исчерпаны | «`/goal все тесты backend зелёные, максимум 5 попыток`» |
| Time-based `/loop` | интервал или самотемп | отмена пользователем / бэклог пуст | разгребание эпика: `/loop возьми следующий таск из docs/PLAN.md по протоколу docs/LOOPS.md` |
| Proactive `/schedule` | по расписанию, без человека | пока не отключён | ночной прогон тестов/линта с записью падений в STATE.md |

Главные требования гайда, зашитые в протокол выше: **детерминированное стоп-условие** (не «сделай хорошо»,
а «тесты зелёные», «чекбокс закрыт», «N попыток»), **верификация как отдельный шаг** и **лимит попыток**.
Когда появится код — оформить проектный verify-skill (как проверять систему end-to-end), чтобы циклы проверяли себя одинаково.

## Ограничители (guardrails)
- Одна итерация = один коммит-кандидат: рабочее дерево после итерации всегда в рабочем состоянии.
- Цикл НЕ трогает: `infra/*.prod.*`, секреты, `DECISIONS.md` задним числом, чужие незакрытые задачи из «В работе».
- Две итерации подряд провалили верификацию одной и той же задачи → стоп по этой задаче,
  записать проблему в «Известные проблемы» и перейти к следующей (не долбить в стену, сжигая токены).
- Деструктивные действия (удаление данных, force-push, изменение прод-конфигов) — только с явного разрешения пользователя.
