# backend/ — Medusa v2 (TypeScript)

> Правила бэкенда. Сопроводительные документы (`docs/`, `contracts/`, корневой CLAUDE.md) живут в
> основном монорепозитории; в этой копии их нет.

## Конвенции Medusa v2 (обязательны)
- **Модули изолированы**: `src/modules/<domain>/` — свои модели + сервис. Модуль НЕ импортирует другой модуль.
  Связи между моделями разных модулей — только через `src/links/`. Сквозная логика — только в `src/workflows/`.
- **API-роуты тонкие**: `src/api/**/route.ts` валидирует вход (zod) и вызывает workflow. Бизнес-логики в роутах нет.
- **Переиспользуй ядро**: прежде чем писать шаг workflow — проверь Core Workflows Reference; у ядра уже есть
  заказы, inventory с резервами, промо, кредитные линии заказа (store credit в OSS-ядре НЕТ — проверено
  на 2.17.2, кошелёк бонусов — кастомный модуль `bonus`). Не дублируй ядро в кастомных модулях.
- **Админ-экраны**: `src/admin/` — widgets и UI routes на дизайн-ките `@medusajs/ui`. Никаких сторонних UI-библиотек.
  Цвета/шрифт — токены `src/admin/styles/brand.css`, оболочка (роль продавца, порядок сайдбара) —
  `lib/shell-mode.ts` + `styles/shell.css`; всё подключается одним импортом из
  `routes/dashboard/page.tsx`. Произвольные утилиты Tailwind в собранном CSS дашборда недоступны —
  свои метрики задавать классами `sm-*`. Даты — только через `lib/date.ts` (свой
  `toLocaleDateString` в экране = регресс локали). Правила и генератор скриншотов — `src/admin/README.md`.
- **События**: реакции (уведомления и т.п.) — в `src/subscribers/`; периодика (сгорание бонусов, пересчёт скоринга) — в `src/jobs/`.
- **Фича-флаги**: отложенный домен НЕ удаляют — прячут флагом из `src/lib/feature-flags.ts` (сейчас
  `FEATURE_COMPANIES` — юрлица: `company`, `scoring`, кредитный лимит, внутренний АВР). Роуты
  закрывают гейтом `src/api/utils/feature-gate.ts` в `api/middlewares.ts` (404, первым в цепочке —
  раньше `authenticate` и валидаторов); подписчики и джобы выходят проверкой в начале. Панель
  спрашивает флаги по сети (`GET /admin/feature-flags`), витрина и мобильные держат свои копии в env
  сборки. Правило: у флага ОБА пути покрыты тестом — включённый и выключенный.

## Мультипродавец (компании на площадке)
- Компания — модуль `tenant` (витрина и реквизиты) + её **канал продаж** ядра (`tenant.sales_channel_id`,
  уникален). Склад, publishable key и доставка — ядровые сущности этого канала, в модели их нет.
  Завести/обновить компанию, её продавца и сборщиков — `src/scripts/setup-tenant.ts` (данные из env,
  пароль не печатается).
- **Витрина**: продавец запроса = publishable key (`lib/tenants/storefront.ts`). Заголовкам, cookie и
  полям тела, «называющим» компанию, не доверять. Корзину чужого канала не переносить — начинать новую.
- **Панель**: пользователь компании = связь `tenant ↔ user` (`links/tenant-user.ts`). Роль в компании —
  `user.metadata.role`: `seller` ведёт заказ (подтверждение, отмена, перенос, вручение, закрытие),
  `picker` собирает (задания сборки) и отгружает, `driver` везёт и вручает по коду получения. Свои метаданные пользователь компании не правит
  (`own_user`), их ставит площадка. Доступ — белый список по ролям `api/utils/tenant-access.ts`
  (middleware на `/admin/*`): новый admin-роут закрыт, пока его туда не внесли. Роут-список режет
  выборку по `getTenantScope(req)`; роут с `:id` заказа/документа/претензии/задания проверяет
  middleware. Любой сбой проверки — отказ, а не доступ.
- **Сборка**: задания видит только сборщик компании заказа (сборщик площадки — заказы вне компаний) и
  только по подтверждённому заказу; первое взятое задание переводит заказ в «Собирается», последнее
  закрытое — в «Собран». Сайдбар сборщика — «Сборка» (`/app/picker`), «Отгрузка», «Склад» (остатки
  своих складов, цена закрыта) и «Отзывы» (только чтение; модерация отзывов — у площадки).
- **Водитель компании** (роль `driver`, учётка — `setup-tenant.ts` с `TENANT_DRIVER_EMAIL`): в панели
  один экран «Доставка» (`/app/delivery`, `GET /admin/delivery-queue`) — заказы своей компании «В
  доставке» (слот, адрес, телефон, состав, оплата) и вручение по коду получения, который называет
  покупатель (`POST /admin/orders/:id/lifecycle/deliver`). Код получения водителю не отдаётся.
  Отдельное мобильное приложение водителя (`/driver/*`, вход по SMS, пул рейсов) на стенде не выложено.
- **Товары в панели** — только своего канала: ядровый `GET /admin/products` получает
  `sales_channel_id` компании (подмена, не дополнение), `/admin/products/:id/*` чужого товара — 404,
  `/admin/product-variants` компаниям закрыт (по каналу ядро его не режет).
- **Клиенты компании**: связь `tenant ↔ customer` (N:M, `links/tenant-customer.ts`). Продавец видит в
  «Клиентах» покупателей с заказами своего канала и привязанных (`loadTenantCustomerIds`). Новый
  клиент — `POST /admin/tenant-customers` (виджет над списком «Клиенты», workflow
  `create-tenant-customer`): учётка по номеру с `has_account` — её же находит вход по SMS. Номер уже
  есть на площадке — молча привязывается, дописываются только пустые ФИО и адрес (правило
  `lib/tenants/tenant-customer.ts`); ответ одинаков, чтобы не выдавать покупки у других компаний.
- Цены общие для площадки: продавец компании правит только остатки своих складов (`price_locked`).
- **Интеграция с 1С** (модуль `onec`, `lib/onec/`, экран `/app/onec`): у компании может быть своя база 1С,
  и тогда её каталог повторяет 1С — товары (только в канале компании, `product.metadata.source = "1c"`),
  цены и остатки приходят синхронизацией (`jobs/sync-onec.ts` по `interval_minutes`, кнопка в панели,
  `scripts/setup-onec.ts`). Два сервиса: номенклатура (`base_url`, …/getxtsitems) и необязательные
  остатки/цены (`stock_url`, …/getitems: `id`/`warehouse`/`qty`/`rate`), сводятся по коду; пустые
  остатки игнорируются. `rate` — учётная цена (себестоимость): ценой продажи она не становится (наценки нет,
  цену продавец ставит сам, решение 2026-10-27); хранится в `onec_item.cost` и видна только в панели
  колонкой «Себестоимость» (наибольшая учётная среди складов).
  Цену и остаток 1С ведёт, только если присылает их (`metadata.onec_fields`):
  тогда на «Ценах и остатках» они только для чтения, иначе их задаёт продавец компании (и цену своего
  товара тоже — в отличие от общих товаров площадки); с появлением цены товар сразу публикуется
  (`lib/onec/publication.ts`). Модерацию такие товары не проходят (подписчик `product-updated` их пропускает). Пустой ответ 1С каталог не трогает;
  пропавшая позиция снимается с витрины (draft), не удаляется. При `exclusive_catalog` после удачной
  синхронизации общий каталог площадки уходит из канала компании. Продавец компании видит в
  «Ценах и остатках» и на витрине только товары и склады своего канала. Пароль 1С — шифром
  (`ONEC_SECRET_KEY`, иначе от `JWT_SECRET`). Сквозная проверка на локальной базе — `scripts/smoke-onec.ts` (выгрузка с ценами) и
  `smoke-onec-bare.ts` (без цен, как у ORGSTROY).
- **Каталог из Excel** (компания без 1С): то же подключение `onec_connection` с `source = "file"` —
  без адреса и пароля, по расписанию не синхронизируется. Файл (.xlsx/.xls/.csv) загружают на экране
  «1С и Excel» (`POST /admin/onec/file`: `apply=false` — разбор, `true` — загрузка) или скриптом
  `scripts/import-catalog-file.ts`; разбор — `lib/onec/file-feed.ts` (строка заголовков ищется по
  синонимам колонок, шапка и «Итого» пропускаются), дальше путь синхронизации 1С целиком. Каждый
  файл — полный каталог. Товары помечены `metadata.onec_feed = "file"` («из Excel» на «Ценах и
  остатках»). Шаблон — `GET /admin/onec/template`. Сквозная проверка — `scripts/smoke-onec-file.ts`
  (только на копии базы).
- Миграции в контейнере: `DATABASE_URL` с `?sslmode=disable` — без него Medusa включает SSL для любого
  хоста, кроме localhost, и `db:migrate` зависает на «Running migrations...» (так и было «известное
  зависание» в deploy-server.sh).
- Реквизиты продавца в документах — одно правило `lib/tenants/requisites.ts` (заказ компании — целиком
  её реквизиты).
- **Оплата** (модуль `order_payment`, `lib/payments/`, `workflows/payments/`, экран `/app/payments`
  «Оплаты и долги»): деньги идут на счёт продавца, единого мерчанта площадки нет (решение
  владельца 2026-10-27). Способы задаёт продавец в настройках своего канала (`payment_settings`):
  **Kaspi QR** (ключи Kaspi у каждого продавца, шифром; провайдер `pp_kaspi_kaspi` берёт их по
  `data.sales_channel_id` сессии через зависимость платёжного модуля на `order_payment`),
  **перевод на номер Kaspi** и **в долг** (`payment-offline`: `pp_transfer_offline`,
  `pp_debt_offline` — авторизуются при оформлении без денег). Без настроек — только Kaspi QR.
  Выбор способа — `POST /store/carts/:id/payment-method` и инструмент чата `checkout_payment`;
  оформление пускает только эти три провайдера (`ensure-cart-payment-authorized`), ядровые
  `POST /store/carts/:id/complete` и `/store/payment-collections/:id/payment-sessions` закрыты.
  У заказа — строка `order_payment` (способ, суммы, срок долга) и журнал `payment_entry`
  (поступления и возвраты; записи не правятся). Перевод: заказ не подтверждается, пока продавец
  не отметит поступление. Долг: подтверждение заказа = одобрение со сроком (отказ — отмена);
  погашения частями. Отмена заказа с полученными деньгами → «нужно вернуть». Бонус за неоплаченный
  заказ не начисляется. Регион получает провайдеры скриптом `scripts/setup-payment-methods.ts`
  (шаг выкладки). Сквозная проверка — `scripts/smoke-payments.ts` (только на копии базы).
  **Чеки Kaspi покупателей** (`payment_receipt`, `lib/payments/receipt-ai.ts` + `receipt-checks.ts`):
  по переводу и погашению долга покупатель присылает снимок/PDF чека (страница заказа —
  `POST /store/orders/:id/payment/receipts`, чат — инструмент `submit_payment_receipt` с вложением
  хода). Gemini читает чек, проверки сверяют сумму, получателя (видимые цифры скрытого номера и
  имя), дату (не раньше заказа, не в будущем), номер квитанции и файл (повтор у другого заказа),
  статус операции и признаки правки. Нарушение → `flagged`, иначе `pending`; деньги чек не
  двигает — продавец засчитывает (запись журнала) или отклоняет с причиной. Аккуратную подделку
  проверки не исключают — последнее слово за продавцом и его приложением Kaspi.
  Покупателю признаки правки не показываются.
  Webhook'и Kaspi продавцов и официальный транспорт Kaspi — после договора: до тех пор оплата QR
  узнаётся опросом статуса, а `kaspi-http-client.ts` — НЕофициальный API, на реальные деньги не
  включать.

## Выкладка изменений схемы
Прод мигрирует с `--skip-scripts` (`scripts/migrate-remote.sh` монорепозитория): `src/migration-scripts`
там НЕ запускаются (а `initial-data-seed` засеял бы стартовый каталог). Перенос данных — отдельный
скрипт `npx medusa exec ./src/scripts/<...>.ts` явным шагом выкладки.

## Прод-сборка выбрасывает каталоги `test`
`medusa build` не компилирует каталоги и файлы с именами `test`, `unit-tests`, `integration-tests`
(build-tools/compiler.js). Роут `src/api/**/test/route.ts` работает в `develop`, но на стенде отвечает
404 — так было с `/admin/onec/test` (переименован в `/check`). Каталоги роутов так не называть.

## Структура src/ (фиксирована фреймворком)
`modules/` · `workflows/` · `api/{store,admin,driver,webhooks}` · `links/` · `subscribers/` · `jobs/` · `admin/` · `scripts/`

## После изменения API
Перегенерируй `contracts/openapi.json` и Dart-клиент (команды — в корневом CLAUDE.md после настройки конвейера).

## Тесты
Интеграционные тесты модуля — рядом с модулем (`src/modules/<domain>/__tests__/`); тесты workflows —
`integration-tests/`. Минимум на модуль: happy-path сервиса + инварианты из docs/modules/<domain>.md.
